## 2. ゲームの流れ（1 挑戦 ≒ 80 秒）

```text
打席前 ─ 打席に立つ（挑戦 -1）─▶ 1 球目 … 10 球目 ─▶ 結果（スプレーチャート）─▶ もう一回 / ホームへ
                                  │
                                  ├ 投球（投手のモーション 0.8 秒 → 的が出る → ボールが到達するまで 1.2 秒）
                                  │   この 1.2 秒で指を押したままずらし、カーソルを的（ボール）へ寄せて少し下に置く
                                  ├ 判定（指を離した瞬間。タイミング ±25/60/110ms + 離したときのカーソルの位置）
                                  ├ 当たり以上 → 外野カメラ（3〜4 秒: 打球の方向へカメラが追う → 落下点 or 柵越え → 距離）
                                  │  ファウル  → 「ファウル」の文字 + 打者が振り向く（1.2 秒）。距離 0 として内訳に残る
                                  │  空振り    → 打者が困り顔（0.8 秒）だけで次の球へ
                                  └ 打席へ戻る（0.6 秒）                     ＝ 1 球 5.6〜6.6 秒（空振り 3.4 秒・ファウル 3.8 秒）
```

- 10 球で 52〜62 秒（`34` の構成 = 当たり以上 8・空振り 1・ファウル 1）。打席前後の画面と球の間の一呼吸を足して **1 挑戦 ≒ 80 秒**（1 回目の 75 秒から少し伸びる）
- **アウトは無い**（10 球必ず投げ切る）。ファウル・空振りは距離 0 として内訳に残る
- 飛距離は判定と能力値で決まり**乱数を混ぜない**（メモの「通貨 = 飛距離÷10 + HR×5（乱数なし）」を引き継ぐ）。
  方向と角度も入力だけで決まる。**「同じ入力なら同じ結果」**が腕前の表現の前提
- ボールのコースは 9 分割のゾーンのどこかに来る（第 1 弾は 10 球の並びを固定 = メモの「きょうの配球」の受け口。
  乱数を使わないので毎日同じ 10 球で全国が競える）
- 柵は方向で変わる（両翼 100m・中堅 122m・左中間/右中間 116m）。球場の拡張（天候・季節・別球場）はこの関数を差し替える

### 2.1 第 1 弾に要る受け口（メモの「拡張 5 軸」のための設計の約束・実装 Issue に転記する）

体験版で作る範囲は小さいが、次の 8 点だけは最初から形にしておかないと第 2 弾で作り直しになる（メモ 2026-09-12 に 3 回目の 2 点を足した）。

1. 飛距離の式の入力を**能力値の構造体 1 本**にする（パワー・ミート・バットの 3 系統が育成 → バット収集 → 打者キャラへ広がっても式を触らない）
2. `Stadium`（**方向 → 柵の距離の関数**・天候）と `Pitch`（球速・**コース**・変化）を**型として持ち、第 1 弾は固定値**を渡す
3. 判定の入力は**タイミング + カーソル座標（x, y）の 3 値**で保存する（3 回目で Y は「捨てる」から「使う」に昇格。解析にも `game_end` の内訳として残す）
4. 保存データに **`schemaVersion` と将来フィールドの空配列**（解放した球場・バット・称号）を最初から入れる
5. 絵は **Art 記述子経由**で描き、座標の直書きをしない（球場・打者の差し替えを可能にする）
6. **外野カメラ層を第 1 弾で作る**（3D ならカメラの位置を打球方向で決めるだけ。`33`）
7. 「10 球」を**定数化**する（配球の拡張で球数が変わりうる）
8. **打球の結果は（方向・距離・種別）の 3 つ組で持つ**（スプレーチャート・称号・球場拡張がすべてこれを読む）

加えてメモの重大制約 2 点（通貨の天井が早い → 第 2 弾のシンクを 3〜4 週で出す前提 / 順位表は規定能力換算で送る・
GC の ID は登録後変更不可）と経済の穴 3 点（時計操作 / 「プレイ記録を消去」で補充されない台帳 / 挑戦回数は開始時減算）は
§3.4 と §6 に反映してある。

## 3. 画面設計の要点

### 3.0 打席の構図（センターカメラ・会長指摘 2026-09-24 への回答）

1 回目の横視点は「投手の位置がおかしい・打者が正面を向いていない・位置関係が良くない」と指摘された。3 回目は
**中継のセンターカメラ**にした（`31`）:

- カメラはセンター側の遠く（本塁から 43m・高さ 6m）に置き、**望遠（垂直画角 9.6°）**で投手と打者の大きさの差を縮める。
  投手は画面の下端に頭と肩・腕だけ映り（背中。マウンドは体に隠れる）、打者は画面の中央やや下に**正面向き**で立つ。捕手はその奥。
  カメラの光軸を本塁の真上に通してあるので、**マウンド → 本塁 → 捕手が画面の縦一直線**（中央の列）に並ぶ
- 打者は右打席で、胸を少し一塁側に開いて顔をカメラへ向ける（現実の構えを崩さずに顔を見せる角度）
- ボールは投手の手（画面の下）から打者（奥）へ飛ぶ。奥へ行くほど小さくなるので、**縮む輪と同じ方向に見える**
  （1 回目の横視点では輪の縮みとボールの移動が別方向だった）
- 捕手側カメラ（パワプロの打席画面）も検討したが、打者の背中しか映らず「おじさんの顔が主役」にならないので不採用。
  打席の主役はキャラ、投手は「柵」の一部という 1 回目の整理を優先した
- **捕手（4 回目・会長決裁）**: 3 回目の捕手（青い塊に黒い板）は不採用で、社長側参考ブランチ `docs/1316-homerun-3d-two-axis` の
  `22-at-bat-3d.jpg` / `28-character-3d.jpg` の見え方に寄せて 3D で組み直した（`mock3d.swift` の `catcherNode()`）:
  白い太ももを左右に開いたしゃがみ・グレーのレガースと膝当て・紺の胸当て（上に薄い紺の帯）・スカルキャップ +
  **ケージ付きマスク（角丸の枠 + 横棒 3 本 + 縦棒 2 本。顔はケージ越しに見える）**・左手（画面右）に大きな茶のミット・
  右手は膝。**審判**（チャコールの服・同じケージマスク・前かがみ）も捕手の後ろに置いた（ほとんど隠れる「野球らしさ」の部品）。
  どちらも判定には関わらない。参考ブランチ自体はマージしない（README §8）
- HUD は上端（球数 / 今回の合計 / 柵越え本数 + 直前 2 球のチップ）と下端（**案内 1 本と、押している指の残像だけ**。4 回目で
  親指 2 本の受け口を外した）に寄せ、中央の打者とゾーンに被せない。上端は背景の客席がうるさいので黒の薄いグラデーションを敷く

### 3.1 判定（2 軸: いつ振るか × どこで捉えるか・会長指摘 2026-09-24 への回答）

会長指摘「タイミング 1 軸だけの判定はプレミアムとして成り立たない。方向・角度をちゃんと入れてほしい」を受け、
**タイミング（従来）にミートカーソルを足した 2 軸**にした（`31` `35`）。判定窓（±25/60/110ms）と経済は維持。

**操作（片手・指 1 本。会長決裁 2026-09-24 で確定）**

| 手順 | 操作 | 決まるもの |
|---|---|---|
| 押す | 画面の**下 1/3（ゾーンより下）のどこでもよい**（受け口の円は置かない。ゾーンの上を押しても反応しない = 指で的を隠さない）。押した瞬間から**ミートカーソル**（水色の輪）が指に追従する | — |
| ずらす | **指の移動量だけ**カーソルが動く（トラックパッド式。指の真下に置く方式ではない = 指で的が隠れない）。的の少し下・内側へ | 角度（上下）と方向の一部（左右） |
| 離す | 縮む輪が的に重なった瞬間に**離す = スイング**。離した位置のカーソルで角度と方向が確定する | 飛距離の土台と方向の一部（早い/遅い） |

- **親指 2 本（左でカーソル・右でタップ）は不採用**。「操作はシンプルにしたい」（会長）ため、**補助設定としても持たない**
- 離す操作は押す操作よりタイミングがぶれる（3 回目に 2 本指を推した理由）。**判定窓 ±25/60/110ms はこのまま維持**し、
  実装時に「離す」の実測分布を取ってから窓を動かすかを決める（実装 Issue の受け入れ条件に計測を入れる）。窓を広げる場合も
  的と輪の幾何（下記）は変えず、ジャストの窓だけを ±35ms 程度まで広げる方向で考える
- 押している間にカーソルの感度（指 1pt = カーソル 1pt）を変える設定は第 1 弾では持たない。iPad は画面が大きいぶん同じ比率で自然に大きく動く

- **的**（白い細い輪・線 1pt・直径 46pt）は投球開始と同時に、ボールが本塁上を通る点に出る。9 分割のゾーンのどこかに来る
  （内角低め・外角高め…）。**縮む輪**（コーラル・線 5pt・直径 118 → 46pt・1.2 秒）は的を中心に線形に縮む
- 輪の幾何は 1 回目のまま（2 軸化でここは変えていない。実装 Issue に転記する制約）: 半径は 0.03pt/ms で縮むので、
  当たり（±110ms）は半径 ±3.3pt、ジャスト（±25ms）は ±0.75pt。2 本の線が「重なって見える」のは半径差が 2.5 + 0.5 = 3pt 以内
  （= ±100ms）のときで、当たり窓の内側に収まる。つまり**「輪が的の線と重なって見えたら離す」で必ず当たり以上**になり、
  ジャストは目では追えない幅なので指のリズムで取る報酬になる。**的は細く・動く輪は太く**が原則（的の線を 3pt にすると
  重なって見える幅が 1.5 + 2.5 = 4pt = ±133ms に広がって当たり窓の外に出て「重なったのに空振り」が起きる。1 回目の verifier 指摘で訂正済み）。縮む時間を
  0.8 秒にすると成立しなくなるので第 1 弾は 1.2 秒固定（配球の拡張で変える）。プレイヤーにミリ秒は見せない
- ミートカーソルは投球ごとにゾーンの中央へ戻る（指を押した時点の位置から相対に動く）。1.2 秒のあいだに的まで寄せ、**少し下**に置くのが柵越えの基本。
  投球前から押していてもよい（押した瞬間に振ってしまう事故が無い = 離した瞬間だけが判定）
- 押さずに投球を見送った場合は**空振りと同じ扱い**（距離 0・内訳に ×）。「見逃し」を別の種別にはしない（結果の凡例・受け口 8 の種別を増やさない）

**角度 = カーソルの高さ**（ボールの中心からの上下のずれ。帯の幅はゾーンの 1/4 ≒ 22pt）

| カーソルの位置 | 打球 | 角度 | 飛距離の係数 |
|---|---|---|---|
| ボールの上 | ゴロ | 0〜10° | 0.3（柵越えにならない） |
| 真ん中 | ライナー | 10〜25° | 0.85（速いが低い。116m 以上でも柵に届かないことがある） |
| **少し下** | **フライ（柵越えの帯）** | **25〜35°** | **1.0** |
| 下すぎ | ポップフライ | 35°〜 | 0.5 |

帯は連続していて隙間が無い（0〜10 / 10〜25 / 25〜35 / 35〜）。境界は上の帯に入れ、係数は帯の中で一定（補間しない。「帯に入ったか」を体で覚えられるようにするため）

**方向 = カーソルの左右 + タイミング**（0° が中堅・負が左）

- カーソルをボールの**内側**（右打者なら打者側）に置くと引っ張り（左へ）、**外側**なら流し打ち（右へ）。最大 ±35°
- 離すのが**早い**と引っ張り側、**遅い**と流し側へ最大 ±15°（当たり窓 ±110ms の端で ±15°）
- 合計が **±45° を越えるとファウル**（距離 0・内訳に「ファウル」）。最大は 35 + 15 = 50° なので、**目一杯ずらして早く（遅く）
  振ったときだけ**ファウルになる（両側で起きる: 目一杯引っ張って早く振る / 目一杯流して遅く振る。欲をかいたときの罰で、真ん中付近では起きない）。柵は**両翼 100m・中堅 122m**
  （`fence(θ) = 100 + 22 cos 2θ`）
- **駆け引き**: 引っ張れば柵が近い（100〜110m）が、ずらしすぎるとファウル。センターは遠い（122m）がファウルが無い。
  「ナイスで引っ張って 110m を越える」か「ジャストでセンターへ 122m を越える」かをプレイヤーが選ぶ

**飛距離 = 土台（タイミング）× 角度の係数 × 芯（カーソルとボールの距離）**

- 土台: ジャスト 135m / ナイス 120m / 当たり 100m（能力値のパワーで伸びる。上限はメモの強化設計）
- 芯: カーソルの中心がボールの中心に近いほど 1.0。半径 11pt（ゾーンの 1/8）で 0.8、それより外は当たり判定の外
- 例: ナイス（120）× 柵越えの帯（1.0）× 芯 0.95 = 114m → 左中間（116m）は越えないがレフト線寄り（104m）なら越える
- 乱数は入れない。**同じ入力は同じ結果**（順位表の公平さと「上手くなった」の実感のため）

**方向メーター**（`31` 右上）: 今のカーソル位置と、**いま振ったときのタイミング**（縮む輪の現在位置から早い/遅いを読む）で
決まる打球方向と、その方向の柵の距離を扇の図で出す（早い/遅いが当たり窓の外なら窓の端の値 ±15° に丸める。`31` はカーソルが内側 + 輪がまだ大きい = 早い、で左中間）。初心者が「カーソルを右に動かしたら扇が右に動いた」で 2 軸目を覚える教材。上級者は消せる

**判定のテキストと Reduce Motion**: 判定の語は ジャスト / ナイス / 当たり / ファウル / 空振り の 5 つ（ミリ秒・角度は
見せない）。Reduce Motion のときは輪の縮小をやめて的の色が変わる方式（1 回目と同じ）。カーソルは動きに頼らないのでそのまま

### 3.2 打席演出（外野カメラ・方向つき）

- 当たり以上で、打球の弧を追ってカメラが外野へ。**カメラの位置は打球方向の線上**（打球の後ろ・少し上）に取り、
  レフト線・左中間・センター・右中間・ライト線のどこへ飛んでもその方向のフェンスが正面に来る（`33` は左中間）。
  **3D ならカメラの座標を打球方向で決めるだけ**で、2D のように方向ごとの背景を描き分けない
- フェンスの**距離表示が方向で変わる**（100 / 116 / 122）。「あと何 m」の緊張感はここで作る
- 柵越えならフェンス上でボールが一瞬止まり、紙吹雪 + 「柵越え！」+ 距離の順（1 回目と同じ）。柵に届かないときは
  落下点でボールが跳ね距離だけ。**フェンス直撃**は新しい結果で、ボールがフェンスで跳ね返る音と「直撃！」を足す
  （柵越えの一歩手前を強く印象づけ、次の挑戦の動機にする）
- 外野手 1 人が見上げる（`33`）。捕球はしない（アウトの無いルールなので追うだけ）。世界（球場）が増えたときは
  スタンド・フェンス・空だけを差し替える
- 音: 芯で捉えた「カキーン」と、柵越えの歓声。合成音の品質が最大リスク（メモの工数 L の理由）。モックでは扱っていない

### 3.3 結果表示（スプレーチャート）

- 最大の数字は**合計飛距離**（順位表に送るのもこれ。規定能力換算はメモの重大制約 2）。柵越え本数はチップに落として主従を付ける
- **どこへ飛んだか**（`34`）: 上から見た扇に 10 球を打点で置く。★ 柵越え・● 当たり・● フェンス直撃・F ファウル・× 空振り。

- 1 球ずつの内訳に**方向の呼び名**（レフト / 左中間 / センター / 右中間 / ライト / 直撃 / ファウル）を足す。

### 3.4 回数回復の導線（体験版の検証設計・会長決裁 2026-09-24 で改定 → 同日 05:41 UTC に本数まで確定）

| 手段 | 付与 | 上限 | 狙い |
|---|---|---|---|
| 無料 | **3 挑戦**（旧 5） | 1 日 1 回リセット（0:00） | 毎日 1 回は必ず遊べる |
| リワード広告 | **+1**（旧 +3） | **1 日 5 本**（確定） | 収益と「広告を見てまで遊ぶか」の測定 |
| アンケート | **+1**（旧 +3・確定） | 1 日 1 回（3 問・30 秒） | 数字に出ない声を集める（会長 2026-09-24 の狙い）。設問は「また遊びたいか / 何が足りないか / 別アプリでも入れるか」から始める |

- **会長決裁（2026-09-24・2 段階）**: まず「広告 1 本で +3 は多すぎる。+1 に」「無料は 3 挑戦」「広告は 1 日 3〜5 本」（2 回目の前）。
  2 回目で当番が広告 5 本・アンケート +1 を推奨し、**3 回目の決裁スレッドへの回答（05:41 UTC）で「広告 5 本/日・アンケート +1 で確定」**。
  合計は 3 + 5 + 1 = **最大 9 回/日**
- 広告を 3〜5 の上限側（5 本）にした理由（記録）:
  1. 体験版の目的は「広告を見てまで遊ぶか」の**測定**で、上限を 3 本にすると 3 本見る人の需要が 3 で頭打ちに記録され、
     4 本目・5 本目を見るかが分からない（打ち切りの数字は下げる判断にしか使えない）。5 本なら実際の分布が読める
  2. 1 挑戦 ≒ 80 秒なので 8 回でも **≒ 11 分/日**。広告 5 本 × 30 秒 = 2.5 分をプレイ 7 分弱に対して見る形で、
     「希少性」（1 日の上限がある）は保てる
  3. 上限は台帳の定数 1 つで、下げるのは後からいつでもできる（上げると「昨日より増えた」が気づかれにくい）
- アンケートを +3 → +1 に揃えた理由（記録）: 会長の表にアンケートの行は無く、30 秒の作業に +3 を残すと「広告 +1 は多すぎる」と
  同じ理由が当てはまるため
- 1 日の最大 9 挑戦 ≒ 12 分。時計操作で無料分を増やしても 1 日 3 回分しか増えない
- **コインで回数は買えない**（本導入でも同じ。買えるのは強さだけ）。画面に明記して経済の意図を伝える
- 挑戦回数は**打席に立った時点で減算**（結果画面で強制終了しても戻らない）。台帳は `PlayLog.allKeys` に
  入れず「プレイ記録を消去」で補充されないようにする（メモの経済の穴）
- 体験版で見る数字: 挑戦回数の消費率（3 回使い切る人の割合）・広告視聴の本数分布（1〜5 本）・アンケート回答率・D1/D7・
  **方向の分布とファウル率**（2 軸目が使われているか）。`game_start` / `game_end` は既存の語彙、`reward_request` の `purpose` に
  `challenge` を足す程度で済む

### 3.6 蓄積の保存量（会長決裁 2026-09-24「ローカル保存量がメモリを圧迫しない設計」）

体験版の蓄積は**通算本数・自己ベスト・順位表・スプレーチャート**の最小構成で確定した。ただし「全履歴を無制限に貯めない・
直近分 + 要約統計中心」が条件。実装 Issue の受け入れ条件に転記する設計:

| 何を持つか | 形 | 大きさ | 使い道 |
|---|---|---|---|
| 通算の要約 | 固定長 1 レコード（挑戦回数・投球数・柵越え本数・合計飛距離の累計・自己ベスト・最長の 1 本・ファウル数・空振り数） | 数十バイト | 打席前「きろく」・称号の将来の受け口 |
| 方向 × 距離帯の集計 | 方向 5 区分（レフト / 左中間 / センター / 右中間 / ライト）× 距離帯 8 段（〜60 / 〜80 / 〜100 / 〜110 / 〜116 / 〜122 / 〜135 / 135〜）の本数 = 40 セル | 160 バイト | 通算のスプレーチャート（濃淡） |
| 直近の挑戦 | **最新 20 挑戦だけ**のリングバッファ。1 挑戦 = 10 球 × 3 値（方向 1 バイト・距離 2 バイト・種別 1 バイト）+ 日時 | 約 1KB | 直近のスプレーチャート（打点）・結果画面の内訳 |
| 日次台帳 | 日付・消費した挑戦数・広告で足した数・アンケート済みフラグ（1 レコード） | 数十バイト | 回数回復の導線 |

- 合計で **数 KB 未満（UserDefaults に置ける大きさ）**。上限（20 挑戦）は定数 1 つで、超えたら古い挑戦から捨てる
- 「蓄積」を将来増やす（称号・球場・バット）ときも、**上の表に行を足す形で固定長か上限付き**にする（第 1 弾の受け口 4 の
  `schemaVersion` と空配列はそのまま）
- 日次台帳は `PlayLog.allKeys` に入れない（「プレイ記録を消去」で補充されないようにする。§3.4）。通算の要約・集計・直近の挑戦は
  `allKeys` に入れて消去の対象にする

- 投手は名無しの白ユニフォーム（帽子つき）。3D では**同じ部品の色替え**（ピンストライプ無し・帽子・茶のグラブ）。

### 4.3 方向A（ドット絵高密度）と方向B（滑らかな塗り）— 2 回目の比較（記録）と会長決裁

2 回目で両方向をユニフォーム姿で作って並べた（`11`〜`16`）。**会長決裁（2026-09-24）: 3D に決定（方向B 採用・方向A 不採用）**。
根拠は「パワプロが 2013 年以降 2D → 3D へ移行し、現行のモバイル版もトゥーン調シェーディングの 3D モデルが基本」。

| 観点 | 方向A: ドット絵・高密度（不採用） | 方向B: 滑らかな塗り（採用 → 3 回目で 3D に） |
|---|---|---|
| 何を変えたか | グリッド約 1.7 倍・縁の陰影・服の描き込み・球場の部品 | 輪郭線なし・グラデーション・落ち影・光沢。3D モデルではなく 3D 風の 2D |
| 描く基盤 | 既存の `PixelSprite` + SpriteKit | SwiftUI の図形 or 外部画像 |
| 「パワプロ」との距離 | 遠い（SFC 版の方向） | 近づくが 3D ではない。カメラが回る・打者が回転する見せ場は作れない |

2 回目の「B は 3D 風の 2D で、本当の 3D にはカメラの自由が無い」という限界を、3 回目は**本当の 3D モデル**で解いた（§4.4）。
ユニフォーム（紺ヘルメット + 黄の中央ライン + 投手側の耳当て / 白ピンストライプ + 黄の V 襟 / 紺ベルト・ストッキング /
黒スパイク / 黄グローブ）は 2 回目の決定をそのまま 3D に写している。

### 4.4 3D の作り方（3 回目・会長決裁「3D」への回答）

3 回目は **SceneKit で球・カプセル・箱・円柱・円錐台・トーラスだけを組み合わせた 3D モデル**を作り、3 段階のトゥーン陰影
（シェーダ修飾子）と輪郭線（反転ハル = 少し大きくした裏面だけを黒で描く）でトゥーン調にした（`mock3d.swift`）。
外部の 3D 資産・画像・フォントは使っていない。**これが「社内で 0 円でできる 3D」の上限の叩き台**で、
以下の 3 経路を比べる材料になる。

| 経路 | 何をするか | 得られるもの | 工数・費用 | 「パワプロ」との距離 |
|---|---|---|---|---|
| **3D-1 社内モデル × リアルタイム 3D** | このモックのモデル（座標と色だけのコード）を **RealityKit** の実体に写し、関節の角度で動かす。カメラも 3D | **カメラが動く**（外野カメラ・打者を回す・柵越えのリプレイ）。ポーズはコマ絵を描かずに補間で作れる。頭身・色・服の変更は数値 1 つ | **L**（描画基盤が新規: トゥーン材質・輪郭線・SpriteKit との共存・iPad の画角）。費用 0 | トゥーン調 3D として同じ土俵。差はモデルの密度（顔の細部・服のしわ・指）と動きの質。**アニメーションは自前のキーフレーム**なので「走る・振る」の自然さは作り込みの量で決まる |
| **3D-1b 社内モデル × プリレンダ** | 同じモデルを macOS で**ポーズごとに画像に描き出し**（このモックと同じ経路）、既存の **SpriteKit** にスプライトとして置く | 3D の見た目を**既存の描画基盤のまま**得られる。実装は走者（チャリンコおじさん）と同じ経路 | **M**（描き出しは生成器、ゲーム側は 2D のまま）。費用 0 | 見た目は 3D-1 と同じ。**カメラは固定**（外野カメラは 2D の演出に戻る = `04` の形）。方向ごとの背景を描き分ける |
| **3D-2 外部制作モデル** | モデラーに依頼したリグ付きモデル（USDZ）+ アニメーションを RealityKit で動かす | パワプロに最も近い密度と動き | **L + 費用**（予算枠 0 円のため**稟議**。金額は未調査で、稟議の前に見積りを取る） | 最も近い。ただし「あそびばの絵柄」から最も離れ、ハブに並んだときの浮きも最大 |

補足:

- **SceneKit と RealityKit**: モックは SceneKit（macOS でヘッドレス描画しやすい）で描いたが、Apple は WWDC25 のセッション
  「Bring your SceneKit project to RealityKit」（developer.apple.com/videos/play/wwdc2025/288/）で SceneKit を**非推奨
  （以後は重大なバグ修正のみ・新機能なし。動かなくなる予定は無い）**とし、RealityKit への移行を案内している。実装で 3D を
  動かすなら **RealityKit を第一候補**にし、トゥーン材質は `CustomMaterial`（Metal のシェーダ）、輪郭線は反転ハルで同じ絵が
  作れる（RealityKit は ECS 構成なので、ノードの親子で組んだモックの構造は実体と部品に組み替える）。
  **モックの座標・色・ポーズはそのまま写せる**（SceneKit 固有の資産は使っていない）
- **3D-1 の中身**: モデルは頭の半径 1 を単位に約 60 個の部品（`mock3d.swift` の `ojisan()`）。ポーズは肘・手・バット先端の
  座標（`Pose3`）だけで、2 点を結ぶカプセル（`limb`）が腕・脚・バットを作る。走者（2D）と同じ「座標 2 点でポーズ」の発想
- **アプリサイズ**: 3D-1 は 0（コード）。3D-1b は画像分（実測: 640×736 の透明 PNG で 1 ポーズ約 50KB。ポーズ数 × 解像度で増える）。3D-2 はモデルとテクスチャ次第（未測）
- **ハブとの一貫性**: どの経路でも「1 本だけ絵柄が違う」論点は残る（2 回目と同じ）。プレミアム枠の印として**意図した差**に
  するなら、ハブのカードにも 3D の顔を使って「この 1 本は別格」を統一する

**決裁（2026-09-24）: 3D-1 で確定**（会長に強い希望なし → 社長判断で当番推奨のまま）。ただし**工数 L のため、着手前に一度
規模感を会長へ確認する**（実装 Issue を起こす前の関所。#1316 の 4 回目の決裁スレッド）。3D-1b は「3D-1 の技術検証で届かなかったとき」の
落とし先として残す（絵は同じものが出る）。3D-2 は体験版が当たってからで遅くない。

**3D-1 の技術的な前提（実装の見積りに効く事実・4 回目に確認）**:

- アプリ本体・`Packages/` に RealityKit / SceneKit / ARKit の利用は **0 件**（SceneKit は `mock3d.swift` だけ）。3D の描画基盤は**ゼロから**になる
- `Packages/GameKit` の配備対象は **iOS 17**。SwiftUI の `RealityView` は iOS 18 からなので、17 を残すなら `ARView(cameraMode: .nonAR)` を
  `UIViewRepresentable` で包む（AR セッション不要）。配備対象を 18 に上げるかは実装 Issue の論点
- トゥーン陰影（3 段階）と輪郭線（反転ハル）は RealityKit では `CustomMaterial`（Metal シェーダ）で出す。**SwiftPM のターゲットに `.metal` を
  置いて Xcode ビルドで `default.metallib` にできるか、`swift test`（macOS・CI）でシェーダ無しでもテストが通るか**は未検証。
  だめなら「3 段の陰影を部品の分割と固定色で焼く（光源固定・カメラは自由）」に落とす。これが**技術検証（段 0）を最初に置く理由**
- SpriteKit の既存基盤（`BlocksView` の「一時停止は `SKView` 側で止める」等の落とし穴）は流用できないので、同種の落とし穴を RealityKit で
  洗い直す（バックグラウンドでの停止・Reduce Motion・iPad の画角）

## 6. 「プレミアムと呼ぶに相応しいか」の判断材料

メモの定義「希少性 × 蓄積 × 演出。閉じても残るものがある」に、3 回目で**腕前の表現**（判定の深さ）を足して比べる。

| 希少性 | ○ 1 日 3 回 + 回復（広告 1 本 = 1 回・上限 5 本）。回数が減る様子（ボールのチップ）を打席前・結果の両方で見せる | ○ 同じ |

  最小の蓄積として**通算柵越え本数に応じた称号**（10 本で「柵越え見習い」…）を体験版に足すかは 1〜3 回目の決裁論点だったが、
