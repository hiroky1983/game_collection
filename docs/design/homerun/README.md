## 2. ゲームの流れ（1 挑戦 ≒ 80 秒）

```text
打席前 ─ 打席に立つ（挑戦 -1）─▶ 1 球目 … 10 球目 ─▶ 結果 ─▶ もう一回 / ホームへ
                                  │
                                  ├ 投球（1.2 秒: 投手のモーション → ボールが的へ。構えの間 0.8 秒を含めて 2 秒）
                                  ├ 操作（押す → ずらす → 離す。離した瞬間 = タイミング、離した位置 = ミート点）
                                  ├ 判定（タイミング: ジャスト ±25ms / ナイス ±60ms / 当たり ±110ms / 空振り
                                  │       ミート点: 方向 = 流し / センター / 引っ張り / ファウル、角度 = ゴロ / ライナー / 打ち上げ / ポップ）
                                  ├ 当たり以上 → 外野カメラ（3〜4 秒: 打球の向きへカメラが振られる → 落下点 or 柵越え → 距離が止まる）
                                  │  空振り・ファウル → 打者が困り顔（0.8 秒）だけで次の球へ
                                  └ 打席へ戻る（0.6 秒）                     ＝ 1 球 6〜7 秒（空振り・ファウルは 3.4 秒）
```

- 10 球で 55〜70 秒、打席前後の画面を含めて **1 挑戦 ≒ 80 秒**（ミート点の操作で 1 球あたり数百 ms 伸びる）
- **アウトは無い**（10 球必ず投げ切る）。空振り・**ファウル**は距離 0 として内訳に残る
- 飛距離は判定窓 × 方向 × 角度 × 能力値で決まり乱数を混ぜない（メモの「通貨 = 飛距離÷10 + HR×5（乱数なし）」を引き継ぐ）
- 柵は方向で変わる: **両翼 100 m・左右中間 ≒ 114 m・中堅 120 m**（`柵(θ) = 100 + 20·cos 2θ`）。第 1 弾は固定。球場の拡張（天候・季節・別球場）は外野カメラ層に乗せる前提
- 第 1 弾は**コース固定（真ん中）**。ミート点の初期位置 = ボールの中心。コース（`Pitch`）は第 2 弾で、的の位置が球ごとに動く形に拡張する

### 2.1 第 1 弾に要る受け口（メモの「拡張 5 軸」のための設計の約束・実装 Issue に転記する）

体験版で作る範囲は小さいが、次の 8 点だけは最初から形にしておかないと第 2 弾で作り直しになる（メモ 2026-09-12 + 今回の 2 軸化）。

1. 飛距離の式の入力を**能力値の構造体 1 本**にする（パワー・ミート・バットの 3 系統が育成 → バット収集 → 打者キャラへ広がっても式を触らない）
2. `Stadium`（**方向ごとの柵の距離**・天候）と `Pitch`（球速・コース・変化）を**型として持ち、第 1 弾は固定値**を渡す
3. **ミート点の座標（的からのずれ）をそのまま保存**する（第 1 弾は方向 5 × 角度 4 の帯に量子化するが、生の座標を残せば帯の境界を後から動かせる）
4. 保存データに **`schemaVersion` と将来フィールドの空配列**（解放した球場・バット・称号）を最初から入れる
5. 絵は **Art 記述子経由**で描き、座標の直書きをしない（球場・打者の差し替えを可能にする）
6. **外野カメラ層を第 1 弾で作り、カメラの向きを打球の方向から決める**（`24` `25`）
7. 「10 球」を**定数化**する（配球の拡張で球数が変わりうる）
8. 打球の結果を **`(距離, 方向θ, 角度, 判定)` の構造体**で持つ（結果画面の散らばり・将来の解析・順位表の換算がこれ 1 本で済む）

加えてメモの重大制約 2 点（通貨の天井が早い → 第 2 弾のシンクを 3〜4 週で出す前提 / 順位表は規定能力換算で送る・
GC の ID は登録後変更不可）と経済の穴 3 点（時計操作 / 「プレイ記録を消去」で補充されない台帳 / 挑戦回数は開始時減算）は
§3.4 と §6 に反映してある。

## 3. 画面設計の要点

### 3.1 判定 = タイミング × ミート点（打席）— 会長指摘 2026-09-24「方向・角度をちゃんと入れる」

**軸 1: タイミング（初回設計を維持）**

- **的**（白い細い輪・線 1pt・直径 46pt・固定）を本塁上のボール到達点に置く。**縮む輪**（コーラル・線 5pt・直径 118 → 46pt）が
  投球開始から到達までの 1.2 秒で線形に縮む。判定窓 ±25 / 60 / 110ms、「重なって見えたら当たり以上」の計算は初回のまま
  （半径 0.03pt/ms・重なって見える幅 ±100ms が当たり窓の内側）。的は細く、動く輪を太く
- タイミングは**初速**を決める: ジャスト 100% / ナイス 88% / 当たり 72%（最大飛距離 140 m = ジャスト・打ち上げ・センター）

**軸 2: ミート点（今回追加）**

- **ミート点** = バットの芯。黄の楕円（30×21pt）で表示し、**指のドラッグと同じだけ動く（トラックパッド式・相対移動）**。
  指がリングに被らない。初期位置はボールの中心（= センター・ライナー）
- **横のずれ = 方向**（右打者）: 内側（体側）にずらすほど引っ張り（左翼方向）、外側にずらすほど流し（右翼方向）。
  ずらしすぎると**ファウル**（距離 0・記録は「ファウル」）
- **縦のずれ = 角度**: 少し下で打ち上げ（一番飛ぶ）、中央はライナー（伸びない）、上はゴロ（柵越え不可）、下すぎはポップ

| 方向（横のずれ・pt） | 帯 | 飛距離 | 柵 | 狙い |
|---|---|---|---|---|
| 内側 +20 超 | **ファウル** | 0 | — | 引っ張りの崖 |
| 内側 +8〜+20 | 引っ張り | ×1.10 | 114 → 100 m（線に近いほど近い） | 一番柵越えしやすいが崖が隣。当たりでもポール際なら越える |
| −8〜+8 | センター | ×1.00 | 114 → 120 m（中堅が一番遠い） | 安全。ジャスト以外は届きにくい |
| 外側 −8〜−26 | 流し | ×0.92 | 114 → 100 m | 帯が引っ張りより広く手堅い。飛距離は落ちる |
| 外側 −26 超 | **ファウル** | 0 | — | 流しの崖（引っ張りより遠い） |

| 角度（縦のずれ・pt） | 帯 | 飛距離 | 柵越え |
|---|---|---|---|
| 上 −6 超 | ゴロ | ×0.30 | 不可 |
| −6〜+6 | ライナー | ×0.85 | ジャストでも中堅は届かない（119 m・フェンス直撃）。引っ張りなら越える |
| 下 +6〜+18 | **打ち上げ** | ×1.00 | ここが本命 |
| 下 +18 超 | ポップ | ×0.45 | 不可 |

- **一番飛ぶのは「ボールの少し下・少し内側」**（`27-mechanics.jpg` の赤枠）。その両隣が崖（ファウル / ポップ）なので
  「欲張るほど危ない」駆け引きになる。センターは崖が無い代わりに柵が一番遠い
- 柵越えの早見（打ち上げ）: ジャストは全方向で越える（センター 140 / 引っ張り 154 / 流し 129 m）。ナイスはセンターぎりぎり（123 m）・
  引っ張り余裕（135 m）・流しは線寄りだけ（113 m）。**当たりは引っ張ってポール際だけ**（111 m vs 柵 100〜111 m）。
  ライナーはジャストの引っ張り（131 m）だけが越える。つまり「タイミングだけ」「ずらすだけ」のどちらでも足りない
- 帯の幅（pt）は指の精度に合わせた叩き台。実装では **生のずれ座標を保存**（§2.1 の 3）して境界を後から動かす
- 画面に出す語は ジャスト / ナイス / 当たり / 空振り / ファウル と、方向（引っ張り / センター / 流し）・角度（打ち上げ / ライナー / ゴロ / ポップ）だけ。倍率やミリ秒は見せない
- タイミングのテキストは打者の上に 0.6 秒、方向・角度はその下に小さく（`23`）。色は ジャスト = `Theme.yellow`、ナイス・当たり = 白、空振り・ファウル = `inkSub`
- 一時停止だけ左上の小さな丸。Reduce Motion のときは輪の縮小をやめ、的の**色が変わる**方式に置き換える（初回設計のまま）

**操作の 3 案**（当番の推奨は案 1。決裁スレッドの論点）

| 案 | 操作 | 利点 | 難点 |
|---|---|---|---|
| **1. 押す → ずらす → 離す**（`27` に図解） | 投球中に画面のどこかを押し、押したまま指をずらしてミート点を動かし、輪が的に重なった瞬間に離す | **片手・1 本指**で 2 軸が決まる。既存の「タップ = タイミング」に近い | 「離す」のタイミング精度は「押す」よりわずかに落ちる（実装で ±10ms 程度の補正を検討） |
| 2. 左手でずらし・右手でタップ | 画面左半分のドラッグでミート点、右半分のタップでスイング（パワプロのスティック + ボタン） | タイミングは初回設計と完全に同じ。投球前からミート点を置ける | **両手**が要る（縦持ちの片手プレイが消える）。誤タップの整理が要る |
| 3. 投球前に狙いを選ぶ | 投球前に「引っ張り / センター / 流し」「打ち上げ / ライナー」を選び、投球後はタップだけ | 一番簡単。宣言の駆け引きになる | 「操作で決める」感が弱く、メニュー選びに見える。技量の伸びしろが小さい |

### 3.2 打席演出（外野カメラ・方向つき）

- 当たり以上で、打球の弧を追ってカメラが外野へ。**カメラの向きを打球の方向 θ から決める**（左中間なら左中間のフェンスが正面に来る）。
  フェンスの曲がり・距離表示・黄のポールで「どこへ飛んだか」が絵で判る（`24` `25`）
- 柵越えならフェンス上でボールが一瞬止まって光り、紙吹雪 + 「柵越え！」+ 距離 + 判定・方向のチップの順に出す
  （数字が最後に出るほうが気持ちいい。会長イメージと合致していることを確認済み）
- ポール際は「ポール際 柵越え！」と見出しを変える（`25`）。切れた場合は同じカメラで「ファウル」と出し、外野カメラは短く（1.5 秒）切り上げる
- 柵に届かないときは落下点でボールが跳ね、距離だけを出す（紙吹雪なし）。フェンス直撃（柵 −3 m 以内）は「フェンス直撃」の一言を足す
- 外野スタンドの客席は色の粒で描く。世界（球場）が増えたときにここだけ差し替える
- 音: 芯で捉えた「カキーン」と、柵越えの歓声。合成音の品質が最大リスク（メモの工数 L の理由）。モックでは扱っていない

### 3.3 結果表示

- 最大の数字は**合計飛距離**（順位表に送るのもこれ。規定能力換算はメモの重大制約 2）。柵越え本数はチップに落として主従を付ける
- 10 球の内訳を**距離 + 方向**で見せ、右に**打球の散らばり**（扇形の落下点・★ 柵越え / ● 当たり / ○ ファウル）。
  「3 球目の 131m がジャストの引っ張りだった」「右に切れたファウルが 1 本」が次の挑戦の動機になる（`26`）
- 「もう一回（残り N）」を主ボタンにして、残り回数を常に見せる。残り 0 なら主ボタンが「挑戦を増やす」に変わり `06-recover` のシートを開く

### 3.4 回数回復の導線（体験版の検証設計・会長決裁 2026-09-24 で確定）

| 手段 | 付与 | 上限 | 狙い |
|---|---|---|---|
| 無料 | **3 挑戦** | 1 日 1 回リセット（0:00） | 毎日 1 回は必ず遊べる |
| リワード広告 | **+1** | **1 日 5 本**（会長指定「3〜5 本」の上限側。下記） | 収益と「広告を見てまで遊ぶか」の測定 |
| アンケート | **+1**（当番判断・要確認） | 1 日 1 回（3 問・30 秒） | 数字に出ない声を集める（会長 2026-09-24 の狙い）。設問は「また遊びたいか / 何が足りないか / 別アプリでも入れるか」から始める |

- **会長決裁（2026-09-24）**: 「広告 1 本で +3 は多すぎる。+1 に」「無料は 3 挑戦」「広告は 1 日 3〜5 本」。合計は 3 + 3〜5 = **6〜8 回/日**
- **広告の本数は 5 本を推奨**（3〜5 の上限側）。理由は 3 つ:
  1. 体験版の目的は「広告を見てまで遊ぶか」の**測定**で、上限を 3 本にすると 3 本見る人の需要が 3 で頭打ちに記録され、
     4 本目・5 本目を見るかが分からない。5 本なら実際の分布が読める
  2. 1 挑戦 ≒ 80 秒なので 8 回でも **≒ 11 分/日**。広告 5 本 × 30 秒 = 2.5 分をプレイ 7 分弱に対して見る形で、「希少性」は保てる
  3. 上限は台帳の定数 1 つで、下げるのは後からいつでもできる
- **アンケートの付与は +1 に揃えた（当番判断・要確認）**。会長の表にアンケートの行は無く、30 秒の作業に +3 を残すと
  「広告 +1 は多すぎる」と同じ理由が当てはまるため。合計は **最大 9 回/日**（≒ 12 分）
- **コインで回数は買えない**（本導入でも同じ。買えるのは強さだけ）。画面に明記して経済の意図を伝える
- 挑戦回数は**打席に立った時点で減算**（結果画面で強制終了しても戻らない）。台帳は `PlayLog.allKeys` に入れず「プレイ記録を消去」で補充されないようにする
- 体験版で見る数字: 挑戦回数の消費率（3 回使い切る人の割合）・広告視聴の本数分布（1〜5 本）・アンケート回答率・D1/D7・
  **方向の分布（引っ張り偏重か）とファウル率**（帯の幅を直す根拠）。`game_start` / `game_end` は既存の語彙、
  `reward_request` の `purpose` に `challenge` を足す程度で済む

### 3.5 HUD とクロームと、打席中のバナー広告（会長の最終決定待ち）

- 打席前・結果は既存ゲームと同じクローム（戻る・？・順位表）とバナー枠
- 打席の HUD は上端に集約し、下端は操作案内だけ。的とミート点は画面の中央やや下（本塁の位置）に置き、
  ドラッグは相対移動なので指がミート点に被らない

**打席中のバナー広告の両論**（`29-banner-compare.jpg`）。会長発言「操作感がわからないが、できれば上部か下部にバナー広告をつけてほしい」は
現行方針「打席と外野カメラだけバナー無し」と矛盾しうるので、決裁を仰ぐ。

| 案 | 見え方 | 利点 | 難点・リスク |
|---|---|---|---|
| **A. 無し（現行方針）** | `22` | プレミアム枠の「格」が絵で出る（既存 20 本はプレイ中もバナーあり）。**押す→ずらす→離す**の指が画面下部を動くので、誤タップの心配が無い | 打席中（1 挑戦 ≒ 80 秒 × 6〜9 回/日）のバナー収入を捨てる。概算: バナー 1 表示 ≒ 0.05〜0.1 円 × 打席中 1〜2 表示/挑戦 × 8 回 ≒ **1 人 1 日 1 円前後**。リワード広告（1 本 1〜3 円 × 最大 5 本）と比べると小さい |
| **B. 下部**（既存ゲームと同じ枠） | `29` 左 | 既存 20 本と同じ位置・同じ実装（Core の `BannerSlot` をそのまま） | **操作領域と隣接**。案 1 の操作は画面下部を押したまま動かすので、離した位置がバナーに掛かると**偶発クリック**になる。AdMob の配置ポリシー（操作の直近に置いて偶発クリックを誘発しない）に触れるおそれがあり、無効トラフィックの控除・警告の実績（`project_admob_safety.md`）を踏まえると避けたい。操作案内をバナーの上に 50pt 詰める必要もある |
| **C. 上部**（HUD を 52pt 下げる） | `29` 右 | 指は下半分にあるので偶発クリックの心配が小さい。収入は B と同じ | 既存ゲームに前例が無い位置（ハブや他ゲームと「同じ役割は同じ見た目」の原則から外れる）。Dynamic Island の直下で視認性は高いが、HUD（球数・合計・柵越え）が 52pt 下がり、客席の上に乗る |

- **当番の推奨は A（無し）を維持**。付けるなら **C（上部）**。B は操作との干渉でポリシーリスクを負う割に収入が小さい
- 外野カメラ（3〜4 秒の演出）にバナーを出しても収入はほぼ増えない（表示時間が短い）ので、A / C どちらでも外野カメラは無しのまま

### 4.5 3D を実際に作るときの道筋（当番の所見・決裁の材料）

このアプリは 20 本以上すべて SwiftUI / Canvas / SpriteKit の 2D で、3D の基盤（SceneKit / RealityKit）は無い。
最低 OS は **iOS 17**（`project.yml` / `Packages/GameKit/Package.swift`）。

| 経路 | 何を使うか | 利点 | 難点・コスト |
|---|---|---|---|
| **(a) 本物の 3D・RealityKit** | `RealityView`（**iOS 18+**）+ USDZ モデル + スケルタルアニメ。トゥーンは Reality Composer Pro のシェーダーグラフ | Apple の現行推奨。カメラが回る・打者が回転する「パワプロ級」の見せ場が作れる | **最低 OS を 18 に上げる必要**（iOS 17 のユーザー比率を確認してから）。**最大のコストはモデル制作**（おじさんのモデル + リグ + 4 モーション + 投手 + 捕手 + 球場）で、社内に制作パイプラインが無い（Blender 技能・予算 0 円。Canva AI は静止画のみ）。外注か学習で **L〜XL** |
| (b) 本物の 3D・SceneKit | `SceneView` / `SK3DNode`（SpriteKit の中に 3D を埋め込める）。iOS 17 で動く | 既存の SpriteKit 資産と最も相性が良い | **WWDC25 で非推奨（deprecated）宣言済み**。動くが新規採用は避けたい。モデル制作のコストは (a) と同じ |
| **(c) 疑似 3D（今回のモックの方式）** | 透視投影で球場を描き、トゥーン調の 2D 部品を奥行きで拡大縮小して置く。SwiftUI Canvas か SpriteKit | **既存基盤で作れる**（工数 M）。外部アセット不要・アプリサイズ影響なし。モックの生成器がそのまま叩き台 | カメラは固定 2 台（センター・外野）。打者の回転・自由なカメラは不可。「3D に見える」上限が今回のモック |
| (d) ハイブリッド | 球場だけ RealityKit の簡単な形状（コードで生成・外部アセット不要）+ キャラは 2D トゥーンのビルボード | カメラが動かせる（外野カメラの追い方が自由になる） | (a) の OS 条件を負う割にキャラは 2D のまま |

- **当番の見立て**: 体験版は **(c) 疑似 3D** で「絵柄は 3D」を達成し、反応が出たら (a) へ投資する順序が自然。
  (c) で作った打席の構図・ミート点・外野カメラ・結果・経済は (a) に移してもそのまま使える（変わるのは描画層だけ）。
  逆に、最初から (a) を選ぶなら**モデル制作の予算と最低 OS の引き上げ**が先に要る決裁になる

## 6. 「プレミアムと呼ぶに相応しいか」の判断材料

メモの定義「希少性 × 蓄積 × 演出。閉じても残るものがある」に当てて、体験版と本導入を比べる。

| 軸 | 体験版（今回の検証形） | 本導入 |
|---|---|---|
| 希少性 | ○ 1 日 3 回 + 回復（広告 1 本 = 1 回・上限 5 本）。回数が減る様子（ボールのチップ）を打席前・結果の両方で見せる | ○ 同じ |
| 技量 | ○ **タイミング × ミート点**。1 軸のときは「同じことの繰り返し」だったが、方向と角度の駆け引きで「上手くなる」余地ができた | ○ 同じ + コースで的が動く |
| 蓄積 | △ **通算の柵越え本数・自己ベスト・順位表だけ**。強化が無いので「上手くなる」以外に残るものがない | ○ コイン・強化 3 系統・（第 2 弾で）球場・バット |
| 演出 | ○ 方向つき外野カメラ・紙吹雪・10 球の内訳と散らばり。ここは体験版でも削らない | ○ 同じ + 球場の差し替え |

- **体験版の弱点は蓄積**。最小の蓄積として通算柵越え本数に応じた称号を足すか、「希少性 × 技量 × 演出」だけで反応を見るかは
  会長判断（初回の推奨「最小」のまま）
- 体験版の反応が薄いときの出口「プレミアム枠を外して通常の無制限ゲームに落とす」は、この設計なら**日次台帳と回復導線を外すだけ**で済む
- 逆に本導入の重大制約（通貨が 14〜39 日で天井・第 2 弾のシンクを 3〜4 週で出す前提）は、体験版のあいだは発生しない

## 8. ファイルと生成手順

| ファイル | 中身 |
|---|---|

| `21`〜`29` の `.jpg` | 3D 方向のモック（JPEG・@2x）。生成器の PNG を `sips -s format jpeg -s formatOptions 82 <in>.png --out <out>.jpg` で変換したもの |
| `01`〜`06`, `08`, `11`, `12`, `14`, `15` の `.jpg` | 初回・2 回目の画面モック（記録） |

- **3D 方向の描き方**: 世界座標（本塁が原点・+Z 投手方向・+Y 上・+X 三塁側）を `Cam`（位置・注視点・焦点距離）で透視投影し、
  球場（客席の粒・壁・芝・土・白線・フェンス・ポール）を投影した多角形で描く。人物は `Rig`（局所座標 → 画面の足元と拡大率）で
  置くトゥーン調の 2D 部品（`drawBatter` は頭身を引数で変えられる）。打席のカメラは `atBatCam`（センター側 50 m・高さ 6.5 m）、
  外野カメラは `Shot`（打球の方向 θ からカメラの位置と向きを決める）
- ドット絵は `PixelCanvas`（楕円・矩形・線を置いて最後に縁取り）で組んでいる。**手描きの `OjisanPixel` と同じパレット**
- 画面はアプリの `Theme`（地 `0xFFF6EC`・文字 `0x4A3B33`・差し色 coral/teal/purple/yellow/pink・角丸 20）に合わせた。フォントは丸ゴシック（`.rounded`）
