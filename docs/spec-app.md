# アプリ全体仕様

## 概要

**アプリ名**: あそびば (Asobiba)
**プラットフォーム**: iOS 17.0+
**向き**: 縦固定 (Portrait only)
**言語**: 日本語・英語（v1.1.12 から。設定画面で選ぶ。仕組みは後述「多言語（#2109）」）
**収益モデル**: AdMob バナー広告 + リワード広告（インタースティシャルは実装はあるがどこからも呼んでいない）

---

### 依存パッケージの版の固定（`Config/Package.resolved`・#1579）

`GameCollection.xcodeproj/` は git 管理外で、`xcodegen generate` のたびに作り直される。Package.resolved がその中にあるため、
以前はビルドごとに Firebase などの版が「`from:` の範囲の最新」へ黙って変わっていた（v1.1.5 は Firebase 12.19.0 で出荷）。

- 版の正典は **`Config/Package.resolved`**（git 管理）。`xcodegen generate` の直後に `bash Scripts/apply-package-resolved.sh` で Xcode が読む場所へ置く（CI・`fastlane beta`・`capture-aso-screenshots.sh` は実施済み）
- CI のビルドは `-disableAutomaticPackageResolution` 付き。`project.yml` の指定と食い違うと落ちる
- **版を上げるとき**: `project.yml` を直し、`xcodegen generate` → `xcodebuild -resolvePackageDependencies -project GameCollection.xcodeproj -scheme GameCollection` で生成された `GameCollection.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` を `Config/Package.resolved` へコピーして同じ PR に含める

### 主要プロトコル

**`GameModule`**: ゲームをプラグイン形式で登録するプロトコル
- `id: String` — ユニーク識別子
- `title: String` — 表示名
- `icon: Image` — ハブカードのアイコン
- `makeView(services:) -> AnyView` — ゲーム画面を生成
  - **呼ぶのは `HubView` の `navigationDestination` 1 か所だけで、必ず `GameScreenHost { module.makeView(services:) }` で包む**
    （#1926）。ハブは描き直しのたびにこの閉包を評価し直すため、素で呼ぶと View の init で作る model が毎回作り捨てられ、
    init の副作用（探索・保存の読み込み・解析 `game_start`）も捨てられる model の分だけ走る。入れ物が画面を最初の 1 回だけ作る。
    **ゲームごとに `.task` で model を遅延生成するなど別の直し方をしない**。新ゲームは `GameModule` を登録するだけで守られる。
    なお `GameServices.gameDidStart` は冪等（`startPlay` が `plays[gameID] == nil` のときだけ数える）なので、
    作り捨てで `game_start` が増えるのは「プレイが終わって `plays` が空の間」に限られる。
    `RecordShareWiringTests` が「作る場所が 1 か所・入れ物に包まれている」ことを走査で固定している
- `hasResumableSnapshot(in:) -> Bool` — 中断データが「続きから」で戻れる**途中の局**か（#809）。既定実装は
  「`resumesFromSnapshot` が true で `snapshots.exists` が true」。**中断データを保存するゲームは、手つかずの盤を保存しない
  （または `hasResumableSnapshot` を上書きして手つかずを除く）**。`snapshots.exists` だけを見る実装に戻すと、
  開いただけの盤が「続きから」になる（#1572・#1599・#1847 で同じ食い違いが別ゲームに繰り返し出た）
- `resumeProgress(in:) -> String?` — 「続きから」の中断データの進み具合 1 行（#2870。`release/v1.1.14` から。既定 nil）。
  ハブのタイルが「続きから」の印の下に出す（NEW・イベントの印が優先のときは出さない）。将棋・チェスは「N手目」、ナンプレは
  「残りNマス」、ポーカー・ブラックジャックの 10 回勝負は「n/10回目」（単発戦は nil）。`hasResumableSnapshot` が true のときだけ読む

**`AdService`**: 広告サービスの境界
- `makeBannerView(width:) -> AnyView?` — バナー広告
- `makeMediumRectangleView() -> AnyView?` — ページ内の 300×250 広告（`MediumRectangleSlot`。既定実装は nil）
- `showInterstitial() async` — インタースティシャル広告（待機付き。プロトコルには残っているが呼び出し箇所は無い）
- `showRewardedAd() async -> Bool` — リワード広告（視聴完了で true）。`GameServices` 経由で
  呼ぶと `game_id` / `purpose` 付きで `reward_ad` イベントも送られる（v1.1.5 からは要求時に
  `reward_request` も。後述の解析仕様）
- `isRewardedAdReady: Bool` — いまタップされたら読み込みを待たずに出せるか（先読み済みか・#658）。
  `reward_offer` の `accepted` / `not_ready` の判定にだけ使う（`release/v1.1.7` から・#780）。
  先読みを持たない実装は既定で true

**`SnapshotStore`**: ゲーム状態の永続化
- `save(_:for:)` / `load(_:for:)` / `exists(for:)` / `clear(for:)`
- 実装: `FileSnapshotStore`（JSON → アプリの Documents/snapshots/）
- `FileSnapshotStore.load` は、ファイルは読めたが decode できないとき、そのファイルを消して nil を返す
  （残すと `exists` が true のまま開始シートが出ず空の盤になる・#1914）。読めない（無い・一時的な I/O 失敗）
  ときは消さない。このため**同じ `gameID` を別の型で `load` しない**こと（大富豪の持ち越しは別 ID
  `<gameID>-carryover`）

### CPU 手番ループの定石（`AITurnGuarded`・#531 / #817・v1.1.5）

CPU は View の `.task(id:)` から起動し、このタスクは**画面を離れる・キーが変わるとキャンセルされる**。
間合いを挟んで手番を連続で進めるモデル（麻雀・花札・大富豪など）は、次の3点を守る。
実装は `Core/AITurnGuard.swift`（`AITurnGuarded` に準拠して使う）。

1. **門番で引き継ぐ**（`withAITurnRunner`）。先行タスクが走っていたら即リターンせず、終了を待ってから
   走者を取る。即リターンにすると「新タスクが即リターン → 先行タスクがキャンセルで抜ける」の順で
   走者不在になり、手番が止まる（大富豪 #287・麻雀 #311・花札 #726）。
2. **sleep の直後にキャンセルを見る**（`pauseCPUTurn(for:)` の戻り値）。`try? await Task.sleep` は
   キャンセルされると即座に返るので、状態の guard だけでは通過し、離れた後に CPU が待ち時間ゼロで
   打ち、その結果が中断データに残る。ループ先頭の判定は無駄な sleep を省く近道で、代わりにはならない。
3. **テストは sleep に入らせてからキャンセルする**。`Task { ... }` を作ってすぐ `cancel()` すると
   本体の開始前に確定し、ループ先頭の判定しか踏まない（#817: 2 の判定を消しても緑のままだった）。
   `await Task { @MainActor in }.value` で本体を sleep まで走らせてからキャンセルし、2 の判定を消す
   変異で赤くなることを確かめる。引き継ぎ（1）のテストは本物のタスクを sleep させず、門番を直接
   立てる（並列実行で待ちが先に切れて空振りする）。どちらも実時間で待たない。

### 計時の共通部品（`GameStopwatch`・#1857・v1.1.10）

計時のある 6 本（数独・フリーセル・ソリティア・スパイダー・麻雀ソリティア・マインスイーパー）は、1 秒ごとのループと
経過秒の取り込みを `Core/GameStopwatch.swift` に寄せている（経過秒の計算は `ElapsedClock`・#1751）。

- モデルが持つのは `elapsedSeconds` と「何を保存するか・いつ決着か」だけ。数える・止める・保存間隔（30 秒）の境目を
  跨いだと知らせる（`advance(from:)`）のは部品の仕事。ループのクロージャは `[weak self]` で渡し、止め忘れてもモデルを握らない。
- 画面側の止め方・動かし方は `.gameTimerLifecycle(rescues:isHeld:pause:resume:)`（`Core/GameClockLabel.swift`）に 1 か所化:
  画面を離れたら止める・背面に回ったら止める・広告のロード〜視聴中は止める・戻ったら再開する。
  「遊び方（？）」のシートは `.howToPlay` が preference（`HowToPlayPresentedKey`）で伝えるので自動で止まり、
  新規ゲーム／開始シートは開閉の `@State` を `isHeld` に渡す（開いたら止め・閉じたら再開・#2406）。時計の見た目は `GameClockLabel`。
- 数独だけは盤の生成が非同期なので、離れている間（`pauseTimer()`〜`resumeTimerIfNeeded()`）に生成が終わった局は、
  保存・計時開始・`game_start` を戻ってきたときまで延ばす（戻らない旧モデルが新しい中断データを上書きしない・#1848）。

### 卓の共通部品（`CardTableSurface`・`CardTableFrame`・`Core/CardTable.swift`・#1501 #1516 #1535 #1536・v1.1.8）

麻雀（4 人打ち）と、ソリティア・スパイダー・フリーセル・麻雀ソリティアの 4 本は、札・牌を**フェルトの卓の上**に置く。
卓の描画は `Core/CardTable.swift` の 1 組が持ち、ゲームごとに別の卓は作らない。

- **色は `CardTableStyle` の 1 か所だけで決める**（木枠 3 色・フェルト 2 色・フェルトの照りの広がり）。呼び出し側が変えられるのは
  形（`CardTableFrame` = 木枠の太さ・内側の影・縦横比・角丸）だけ。盤・駒・牌と同じく**ライト / ダークで変えない**
  （`Theme.Fixed` と同じ扱い）。数値のまま置いてあるのは、`CardTableSurfaceTests` がコントラストを検証するため
- **使い方**: ソリティア系 4 本は盤に `.cardTable()`（形は `CardTableFrame.standard` = 四方とも同じ太さ・角丸 20・外の落ち影あり）を付ける。
  木枠と内側の余白（`contentInset` 6pt）ぶんだけ中身が縮むので、札の大きさを `GeometryReader` で決める盤はそのまま卓に収まる。
  ソリティア・スパイダー・フリーセルは札の最上段を卓の上端から離す（`cardTopInset` 12pt を `topInset:` に渡す）。麻雀ソリティアは山を卓の中央に置くので付けない。
  麻雀（4 人打ち）は上だけ太い木枠・角丸なし・縦横比 1.2 の別の形（`MahjongTableLayout.tableFrame`）を `CardTableSurface` に直接渡す
- **卓の上に乗る「札・牌ではないもの」の色は環境値 `cardTableInk`**（空き枠の破線と印・上段の仕切り・盤の場所に出す文字）。
  既定（`.plain`）は地の上の `Theme.inkSub` / `Theme.ink` の系統で、`.cardTable()` を付けた祖先から子孫へフェルト用（`.felt` = 白の系統。空き枠は
  3:1・文字は 4.5:1 をフェルトのいちばん明るい中央に対して満たす）が配られる。空き枠を描く側（`CardSlot` など）は「卓の上か」を知らなくて済む。
  環境値は祖先から子孫へしか流れないので、**子に付けた `.environment` は親の `@Environment` には届かない**（色は盤の**中**で `CardTableInkReader` を使って読む）
- 木枠の太さと内側の影は、麻雀とソリティア系で同じ比（`CardTableFrame.Length` が固定 pt か卓の幅に対する比のどちらかを持つ）

### 3D 描画基盤（RealityKit・`GameHomerun/Toon3D/`・#1479 #1480 #1481・`release/v1.1.7`）

柵越えおじさんの球場・おじさん・打者・投手・捕手・審判は、**アプリで初めて RealityKit の 3D で描く**
（ほかのゲームは SwiftUI / SpriteKit の 2D）。絵柄は `docs/design/homerun/`（`README.md`・`mock3d.swift`）で決めたトゥーン調で、
`mock3d.swift`（SceneKit のモック）の `sphere` / `box` / `limb` / `bat` を `HomerunToonModel` に写してある。

- **描画は `ARView(cameraMode: .nonAR)` を `UIViewRepresentable` で包んだもの**（`HomerunToonSceneView`・`HomerunAtBatSceneView`・
  `HomerunOutfieldSceneView`）。`RealityView` は iOS 18 からで配備対象（iOS 17）に置けないため。AR セッションは使わない
  （`automaticallyConfigureSession: false`）。背景は透明にして SwiftUI 側の空色のグラデーションを見せ、
  モーションブラー・被写界深度・HDR・接地影などのレンダーオプションは切ってある
- **形は RealityKit に依存しない純粋な値で作る**（打者を除く。打者は下の Meshy 製 USDZ を読むので、この性質は成り立たない。`HomerunToonMesh` = 頂点・法線・陰影の u・縞の v・添字、`HomerunToonModel` = 色ごとの部品の並び）。
  `HomerunToonScene` がそれを `MeshResource` / `ModelEntity` に変えるだけなので、形・配置・陰影の段は `swift test` で固定できる
  （`HomerunToonMeshTests`・`HomerunStadium3DTests`・`HomerunOutfieldLayoutTests`）。
  座標はメートル（本塁が原点・+z がセンター・+x が一塁側）。おじさん単体は頭の半径 = 1 の単位で組み、置くときに縮尺を掛ける
- **トゥーン陰影**: 頂点の `u` に「法線・光の向きの内積」（0 以上に切る）を焼き、**暗・中・明の 3 段の階段状ランプ画像**
  （`u` が 0.18 以下 = 明るさ 0.6、0.18〜0.5 = 0.78、0.5 超 = 1.0）を引いて、部品の色（tint）を掛ける。光源はモデルに対して固定
  （カメラの左上手前）。ランプ画像は `CGImage` からコードで生成する（白のジャージの縞つきの 1 本を含む）。
  **Metal のシェーダ（`.metal`）は使わない**: SwiftPM の `.metal` は Metal Toolchain の無い環境で `swift test` ごと落ちるため。
  ランプ画像を作れない環境（Metal の無い CI など）では nil になり、色は陰影なしの単色になる
- **輪郭線（反転ハル）**: 部品を一回り大きくした殻の三角形の巻きを逆にし（`HomerunToonMesh.flipped()`）、インク色（`0x2B2634`）で塗る。
  既定の背面カリングで殻の**内側の面だけ**が見えて縁取りになる。材質は陰影・輪郭とも `UnlitMaterial` だけ
- **球場は数千個の箱を色ごとのメッシュ 1 個にまとめる**（`HomerunToonModel.merged()`。輪郭線と縞の無い部品だけが対象）。実体の数を色数まで減らすため
- **macOS では 3D を描かない**（`#if os(iOS) && canImport(RealityKit)`）。おじさん単体（ロビー）は既存の 2D の絵（`OjisanCanvas`）に、
  打席・外野のシーンは空色の背景だけに落ちる。GameKit が macOS 14 でも `swift test` を通す（`Package.swift` の `platforms`）ための落とし先で、アプリ（`project.yml`）の対象は iOS 17 以降
- **打者は Meshy 製の USDZ**（v1.1.8・`Resources/HomerunBatter.usdz`・`HomerunBatterAsset` / `HomerunBatter3D.swift`）。パッケージの素材として読み込み
  （`Package.swift` の `resources`）、**材質（PBR のもの）は読み込み後にすべて `UnlitMaterial` に置き換える**（テクスチャの色をそのまま出す = 光に左右されない。PBR のままだと照明しだいで暗く沈むため。
  テクスチャには明るさ 0.96 を掛けて球場の明るい段に合わせる）。骨の動きは Blender で 1 本の右打ちスイング（1〜44 コマ）に空振りの演出（45 コマ目〜・`HomerunWhiffGag`）を続けたクリップ 1 本で、
  構え・溜め・スイング・空振りはそのクリップの区間を切って再生する（モデルは 1 つ）。**読み込めない（`Entity.load` の失敗・アニメ無し）ときは、
  プリミティブで組んだ旧モデルに落とす**（`HomerunBatterRig.init?` が nil → 呼び出し側（`if let rig = HomerunBatterRig()` の else）が旧モデルを使う）。打者の形は USDZ の中身なので、`swift test` では形ではなく
  動きの区間・打点の同期（`HomerunSwingContact`）を固定する
- **打席のカメラは前 / 後ろの 2 択**（#1506・`HomerunAtBatLayout.CameraPreset`）。前は中継のセンターカメラ（本塁から 28m・高さ 4.5m・望遠）、後ろは本塁の 5.5m 後ろから
  ストライクゾーンを見下ろす（画角 50°。捕手の肩越し）。一時停止の画面で切り替え、**選んだ方は `UserDefaults` のキー `homerun_atBatCamera_v1` に保存して次回も使う**
  （既定は前・`HomerunModel.atBatCamera`）。見た目だけで、判定・座標・解析は変えない（投球中に切り替えても同じ球のまま続く）。
  3D の球は 2D の的に重なって映るよう、カメラごとに着く点を計算する（#1647）
- **結果画面のおじさんは 1 枚絵**（`HomerunOjisanStillCache`・`HomerunOjisan3DStillView`）。小さな枠のために RealityKit を回し続けず、構えを `ARView` から画像に落として出す。
  画像は打席前のおじさん（`HomerunOjisan3DView`）が描いたついでに作ってプロセスの間だけ持つ（結果画面を開くときに `ARView` を作ると主スレッドが止まるため）。
  打席前を通らずに結果へ来たときだけ、結果画面で 1 枚描いてから画像にする。macOS の `swift test` では 2D の絵（`OjisanCanvas`）に落ちる
- 3D の描画は VoiceOver から隠す（`accessibilityHidden`）。打席の操作・結果は 2D の SwiftUI 部品が受け持つ
- 外野のシーンは**静止ショット**（当たり以上でカメラが切り替わり、方向の柵・外野手・打球の落下点 / フェンス直撃 / 柵越えの位置が 1 枚で見える）。
  軌道の連続アニメーションは持たない。乱数なしで、同じ `HomerunBattedBall` は同じショットになる

### ゲーム画面のレイアウトパターン A（全画面・バナー下・タイトルあり。#2111 / #2531・v1.1.14）

ゲーム画面の組み方は A〜D の 4 パターン（会長 2026-10-08・#2111）: **A. 全画面**（盤・卓を画面いっぱいに広げる）/
**B. 盤＋バナー**（従来の組み方）/ **C. 盤＋大きいバナー**（盤の下が余るゲーム。バナーの大きさは会長決裁待ち）/
**D. 独自**（柵越えおじさんだけ）。割り当ては `docs/design/layout-patterns-2111/` のモックを見て会長がゲームごとに決める
（2026-10-19 時点で A に決まったのは いろリレー・大富豪。2048・15 パズル・マインスイーパーは今のまま（ルーレットは #2545 で削除）。
ブラックジャックは #2426 で決裁待ち）。

**A の共通枠**は `Core/FullScreenGameChrome.swift` の `gameChrome(title:review:fullScreen:ads:reference:newGame:status:)`
（通常の `gameChrome(title:review:…)` の代わりに 1 回だけ通す。走査テスト `GameChromeSourceTests` の「ちょうど 1 回」はどちらの形も
同じ 1 回に数える）。会長決裁（2026-10-18/19）どおり:

- **OS のナビゲーションバーを出さず、自前の 1 行のヘッダー**（44pt の行 + 上下 4pt = 52pt。iOS 26 のナビバー 54pt より低い）に
  **戻る ＋ ゲーム名（左寄せ。長いと縮めて 1 行）＋ 札（ゲーム数・手番などの状態。`GameStatusBar` に置いていた中身）＋
  役の早見表 → ？ → 新規**を詰める。右の並びは通常の枠と同じで、ゲーム側からは変えられない。札はヘッダーの残りの幅を受けるので、
  英語の iPhone SE のように足りないときはゲーム側が `ViewThatFits` で短い言い回しに切り替える
- **面を画面全体に敷く**（`FullScreenGameSurface`）。カード系は共通の卓のフェルト（`CardTableStyle`・木枠なし）で、
  卓の上の文字色（`cardTableInk`）も枠が配る（盤に `.cardTable()` を重ねない）。それ以外は地の色
- **バナーは画面最下部の地の色の帯**（上 8 + 50 + 下の安全域。`safeAreaInset`）。ゲーム側には `BannerSlot` を置かない。
  フェルトは広告の裏までは敷かない（広告の面に卓の色が混ざらない）
- 左右の余白は 8pt（通常の 16pt より詰める）。寸法は非隔離の `FullScreenGameLayoutMetrics` に置き、
  盤・操作の段に使える高さ（iPhone 17: 668pt / SE: 537pt）と盤に残る高さの計算を `FullScreenGameChromeTests` が値で固定する
- 操作の段の高さは枠では決めない。盤が決着後も残るゲームは従来どおり `GameControlArea` で「決着しても盤が動かない」契約（#148・#1485）を守る
- **ステータスバーの文字色**: iOS 26 では隠したナビバーの `toolbarColorScheme(.dark)` が効いて白くなる。iOS 17 では効かない
  （SE で実測）ので、26 より前はフェルトをステータスバーの裏まで敷かず地の色のまま（黒い文字が読める）

A に載せる対戦ゲームの**相手（CPU）の席**は共通部品 `OpponentSeat`（`Core/OpponentSeat.swift`）: 色と記号の丸いアイコン
（`OpponentSeatIcon`。桃の星・墨の月・生成りの雲）・手番の黄色い輪・裏向きの札の束（`OpponentCardFan`。札の裏はゲームごと）・
残り枚数（1 枚は黄色の札）・直前の手の吹き出し（空でも高さを残す）。いろリレーの見せ方（#2369）を大富豪にも使う
（会長指示 2026-10-19）。読み上げ文はゲーム側（`*Accessibility.seatLabel`）が渡し、手番を必ず文に入れる（#2495）。
フェルトの上で出せない札を沈めるときは不透明度を落とさず `View.tableDimmed`（白を重ねる）を使う（紙が緑に濁らない）。

## リザルトの枠（レコメンド・難易度の階段）

#722・#917。`release/v1.1.5` から。各ゲームのリザルト直下の枠（`Core/RecommendationCard.swift` の `RecommendationSlot`）には、
決着後に次の順で**1枚だけ**出す。

1. **レコメンド**（別のゲームを勧めるカード）。決着の時点で提示済みとして数える（`PlayLog.markShown`）ので、
   出せるときは常に優先する（隠すと「見せていないのに無視された」回が積み上がる）
2. **難易度の階段**（#722）。レコメンドが無いときだけ出す
3. どちらも無ければ**何も出さない**（#917。以前は「ほかのあそび」＝ハブへ戻るだけのボタン・#661 を出していたが、
   左上の戻ると同じ出口のため 2026-09-15 の会長 QA で取り下げた）。枠の高さはひな形（`RecommendationCard.heightPlaceholder`）が
   確保しているので、何も出なくても周りの寸法は動かない

階段の規則は `Core/DifficultyLadder.swift`（乱数を使わない純粋関数。保存キーを増やさない）:

- **出す条件**: その回の決着を記録した連勝数（`PlayRecord.currentStreak`）が `streakThreshold`（3）の倍数のとき
  （3・6・9…連勝）。連勝は勝ち以外で 0 に戻るので、出るのは勝った回だけ。最上級で遊んでいるとき・プリセットに当たらない盤
  （マインスイーパーの旧サイズの中断データなど）では出さない
- **出し直しの間隔**: 提示間隔を連勝数そのもので持つので、勧めを使わずに同じ段で遊んだ人に次の勝ちで出し直すことは無い
  （次は更に 3 連勝したとき）。×で閉じた提案はその決着のあいだだけ隠れる（決着は `PlayRecord.plays` で見分ける）
- **カード**: 「N連勝中！ つぎは「◯◯」にしてみる？」＋「あそぶ」。押すと一段上の難易度で新しい局を始め、
  `gameDidRestart` を通すので `game_start` の `level` はその段で送られる
- **連敗で一段やさしい段を勧める**（#2614。`release/v1.1.14` から）: 連勝と同じ `streakThreshold`（3）の倍数の**連敗**（`PlayRecord.currentLossStreak`。
  負けで +1・勝ちか引き分けで 0。旧データには鍵が無いので Optional で、nil は 0 連敗）のとき、一段下を勧める
  （`DifficultyLadderOffer.direction == .down`・見出し「N連敗中…」・矢印は下向き）。連勝と連敗は同時に成り立たないので排他。
  最下段では勧めない。広告コンティニューで取り消した負けは連敗にも数えない
- **採用ゲーム**（`DifficultyLadderPrompt` を作る View）: 将棋・チェス・囲碁・オセロ・五目並べ・神経衰弱・花札こいこい
  （CPU の強さ）、ナンプレ（難易度）、マインスイーパー（盤のプリセット）。`release/v1.1.14` でソリティア・スパイダー・
  カードしりとり・ぱっと暗算にも配線した（#2599。実際の採用は `DifficultyLadderPrompt` を使う View が正）
- **連勝の単位**は記録の区分（`PlayLog.recordKey(gameID:variant:)`）と同じ。`GameScore.variant` で区分を持つゲームは区分ごとに数える:
  ナンプレは難易度ごと、マインスイーパーは盤の大きさと地雷数ごと、花札こいこいは既定と違うルールの組み合わせごと
  （局数・酒の役・CPU の強さ）。この 3 本は一段上がると別の区分になり、連勝は 0 から数え直す。残りの 6 本は難易度を問わずゲーム単位

## 多言語（#2109・v1.1.12）

日本語（開発言語）と英語。**アプリ内で選んだ言語に、再起動なしで即時に切り替わる**。

### 仕組み

- **表示言語** `AppLanguage`（`ja` / `en`）と置き場 `AppLanguageStore.shared`（CoreEngine）。
  - 初期値は端末の言語（`Locale.preferredLanguages` の先頭が日本語なら日本語、**それ以外はすべて英語**）。
    設定画面で選ぶと `UserDefaults` のキー `appLanguage_v1` に保存し、以後はそれが勝つ。
  - アプリ本体が起動時（`GameCollectionApp.init` の先頭）に `AppEnvironment.bootstrapLanguage()` で読み込む。
    動作確認・英語のスクショ撮影は起動引数 `-appLanguage en`（その回だけ・保存しない）。
  - **`swift test` は bootstrap しないので常に日本語**。日本語の文言を確かめている既存のテストは、
    CI の macOS が英語でも結果が変わらない。英語を確かめるテストは `language: .english` を明示して引く。
    テストから `AppLanguageStore.shared` を書き換えない（並列のテストが巻き込まれる）。
- **文言の表** `StringTable`（CoreEngine）。モジュールごとに 1 つ、`Resources/Localization/Localizable.xcstrings`
  （Xcode の String Catalog と同じ形式）を持ち、各モジュールの `Localization.swift` の
  `let tr = StringTable(bundle: .module)` で引く（アプリ本体は `App/AppStrings.swift` の `bundle: .main` と
  `App/Localization/Localizable.xcstrings`）。
  - **キーは日本語の原文**。日本語のときはキーをそのまま返し、英語のときは表の `en` を返す。訳が無ければ日本語のまま。
  - 表は**コンパイルせずに同梱して実行時に読む**（Package.swift は `.copy("Resources/Localization")`、
    project.yml は folder 参照）。Xcode がコンパイルした `.lproj` はシステムの言語で引かれ、アプリ内で選んだ言語に
    追従しないため。同じ JSON を `swift test` とアプリの両方で同じコードが読むので、英語の表示をテストで確かめられる。
  - 即時の切り替えは Observation で行う。`tr(...)` は `AppLanguageStore.shared.language` を読むので、`body` の中で
    文言を引いた View は言語を変えた瞬間に描き直される。根の `.appLanguageEnvironment()` が `\.locale` も配る
    （数字・日付の書式とシステムの部品用）。
- **システムの言語に従うもの**（アプリ内の選択は効かない）: ATT の説明文（`App/en.lproj/InfoPlist.strings`）・
  通知の許可ダイアログなど OS が出す文言、ホーム画面のアプリ名、共有シート。予約済みの通知は**予約した時点の言語**のまま届く。

### 新しい文言の足し方（②〜⑥とそれ以降の全員）

1. ソースでは日本語をそのまま書かず、`tr("日本語の原文")` で引く。`Text(tr("設定"))`・`Button(tr("完了")) { … }`・
   `Label(tr("ヒント"), systemImage: …)`・`.accessibilityLabel(tr("…"))` のように、`String` を受ける初期化子に渡す。
   - 値を埋め込む文は**文字列補間を使わず書式にする**: `tr("「%@」が途中のままです", title)`（文字列は `%@`、
     整数は `%lld`）。英語で語順が変わるなら訳文側で `%2$@ of %1$@` のように位置を指定する。
   - 数で単語が変わる英語は、表の `en` を複数形（`variations.plural` の `one` / `other`）にする。最初の整数の引数で選ぶ。
   - `static let x = "…"` は起動時の言語で固まるので `static var x: String { tr("…") }` にする。
     `public` な関数の既定引数には `tr` を書けない（内部の宣言のため）。`String? = nil` にして本体で `?? tr("…")` にする。
   - キーを変数で渡す（`tr(name)`）と、下の検査が訳し漏れを拾えない。表に載せるキーはリテラルで書く。
2. そのモジュールの `Resources/Localization/Localizable.xcstrings` の `strings` に、キー（日本語の原文）と `en` の訳を足す。
   Xcode で開けば String Catalog の画面で編集できる。JSON を直接書くときは既存の項目の形に合わせる
   （`"extractionState" : "manual"` を付ける。表はコンパイルしないので、Xcode の自動抽出は働かない）。
3. `swift test --package-path Packages/GameKit --filter LocalizationTests` で確かめる。落ちる条件:
   ソースの `tr("…")` のキーが表に無い・英語の訳が無い／空／日本語が残っている・`%@` や `%lld` の種類と数が
   原文と訳で食い違う・キーに文字列補間（`\(…)`）がある・モジュールに表や `tr` が無い／Package.swift で同梱していない。
4. 英語は日本語より横に長い。1 行に収める所（`lineLimit(1)`・幅が固定の枠）は `minimumScaleFactor` か、
   `ViewThatFits` で短い言い回しに切り替える形にして、SE（幅 375pt）で確かめる。

- 「連続日数」タイルは今の連続プレイ日数（`PlayDayStreak.current`・1 日空くと 0）。遊んだ日は `PlayLog.playDays`（直近 366 日ぶん）に保存済みで、**保存項目は増やさない**。
- 副ラベル「最長 N 日」（`release/v1.1.15` から）は `PlayDayStreak.longest(days:today:)`（`current` と同じく今日より未来の日は無視）で開くたびに計算し直す。
  出す条件は `PlayDayStreak.showsLongest`: 最長が今の連続より長く、かつ 2 日以上のとき（今が 0 日でも出す・今が最長なら出さない）。
- 数えられるのは保存している 366 日ぶんの範囲だけ。VoiceOver ではタイトル・値・副ラベルを 1 つに読む。

### 数字・単位・記録の表記（#2168）

数と単位・「ベスト」「最短」をつなげて文にする所は、**語順ごと文言の表の書式で組む**（英語は語順も単位も変わる）。
記録の 1 行（ハブ・リザルト・共有）は `RecordFormat`（CoreEngine）に集約してあり、各関数は `language:` を省略すると
いまの表示言語で出す。日本語の表記は #2168 の前と 1 文字も変えていない（`RecordFormatLocalizationTests` が
前の実装の写しとあらゆる記録の組み合わせで突き合わせる）。

| 表記 | 日本語 | 英語 | 使うもの |
|------|------|------|------|
| 時間 | `1:23` / `1:02:05` | 同じ | `RecordFormat.time` |
| 数 | `12,340` | 同じ | `RecordFormat.number`（整形してから `%@` で渡す） |
| 順位 | `1位` | `1st` `2nd` `3rd` `11th` `21st` | `RecordFormat.rank` |
| 距離 | `1,234 m` | 同じ（数と m の間に空白） | 数は `RecordFormat.number` |
| 回数・手数 | `3回` `24手` | `3 plays` `24 moves`（単数は `1 play`） | 表の複数形 |
| 勝敗 | `3勝5敗1分` | `3W 5L 1D` | `RecordFormat.hubLine` / `resultLine` |
| 平均順位（大富豪・いろリレー・v1.1.14〜） | `3勝5敗1分・平均2.1位` | `3W 5L 1D · Avg. place 2.1` | `GameScore.place` を `PlayRecord.placeTotal/placeCount` に累計（順位の無い旧データは分母に入れない）。#2606 |

- **桁区切りの数は `%lld` にしない**（日本語の表示が変わるため `RecordFormat.number` で整形して `%@`）。
  英語の単数・複数は、表の `en` を複数形にすれば整形済みの「1,234」でも選ばれる（`StringTable` が整数の引数が
  無いときは数字だけの文字列引数を数として読む）。
- 英語の序数は 4 通りに分かれ、表の複数形（one / other）で表せないので、文言の表ではなく `RecordFormat.rank` で組む。
- 区分の表示名（`PlayRecord.variantLabel`・「初級」など）は記録に保存された文字列をそのまま出す（`RecordFormat` では訳さない）。

## ナンプレの難易度（#3099・v1.1.15）

難易度は 4 段（`SudokuDifficulty`）。空きマスの目安は かんたん 30〜35／ふつう 40〜45／むずかしい 46〜50／**上級 52〜56**。
唯一解を保てないマスは削れずに戻すので、実際の空きは上限に届かないことがある（開始シートの表記が「約」なのはこのため）。

- **上級は手筋の下限をそろえる**: 空きの数に加えて、`SudokuEngine.isSolvableBySingles`（単独候補＝そのマスに入る数字が 1 つしか残らない／
  隠れた単独＝行・列・ブロックのどこかでその数字を置けるマスが 1 つしかない、の 2 つだけで最後まで解けるか）が **false の盤だけ**を出す。
  空きが 52 未満か、この 2 つで解けてしまう盤は捨てて、同じ完成グリッドから削り直す（上限 40 回。超えたら最も条件に近い盤）。
  ペア・ポインティング等のどれが要るかまでは判定しない。既存 3 段の生成は従来どおり（空きの数だけ）。
- **唯一解の判定**は、行・列・ブロックの使用済みの数字をビットで持ち、候補が最も少ない空きマスから試す探索（`SudokuEngine.solutionCount`）。
  上級（空き 52 以上）でも生成を 1 秒以内に収めるため（Debug ビルドの Mac で上級 30 盤: 最大 0.30 秒・平均 0.07 秒）。
- **記録は難易度ごとに別枠**（区分キー `easy` / `normal` / `hard` / `expert`・名前は `RecordVariantLabels`）。
  **Game Center の順位表は上級を送らない**（`GameCenterLeaderboard` の表に `expert` を持たない）。ミス 3 回・ヒント・戻すの決まりは他の段と同じ。
- 解析の `game_start` の `level` は上級が `expert`（他の 3 段は `beginner` / `normal` / `hard`）。

## 評価リクエスト（`ReviewRequestPolicy`・#53 / #1471・#3061・#3078）

勝ちの中でも「見せ場」の直後にだけ、OS の評価ダイアログ（`requestReview`）を依頼する。
判定は `ReviewRequestPolicy`（純粋関数）、予定と記録は `ReviewRequestService`、
決着の入口は `GameServices.gameDidFinish`（`isReviewHighlight` 引数）に集約している。

| 条件 | 内容 |
|------|------|
| 1 | 勝利・クリアの直後、かつ**見せ場**のみ（下表）。勝利数は見せ場でなくても従来どおり数える |
| 2 | 通算 5 勝するまでは出さない |
| 3 | 前回から **15 日**以上（#1471 で 120 日→60 日、#3061 で 15 日。OS の上限＝365 日で 3 回に任せる） |
| 4 | 前回から +5 勝以上（#3061 で 20 勝から短縮） |
| 5 | 同一バージョンでは 1 回まで |
| 6 | リザルト表示の 1.0 秒後（進行中には出さない） |

**見せ場**: 全ゲーム共通で次のいずれか（#3097・v1.1.15。CPU の強さに関係なく、下表で絞るゲームでも成り立つ）。
- 得点・最高値・時間・手数の自己ベストを更新した（連勝記録の更新そのものは含めない）
- そのゲームの記録が**ちょうど 3 連勝**に達した（4 連勝目以降は毎回の見せ場にしない）
- Game Center の実績（ゲーム横断の 4 個）を**新たに解除**した（達成済みの再送は数えない。サインイン済みのときだけ。判定は `GameCenterReporter.wouldUnlockAchievement`）

加えて、次のゲームは勝ちの中でも絞る。表に無いゲームは「勝った・クリアした」がそのまま見せ場（既定）。

| ゲーム | 見せ場 |
|------|------|
| ブラックジャック | ブラックジャック（最初の 2 枚で 21）で勝った回を含む 10 回勝負に勝ち越した（#2552。1 回ごとの決着は記録・評価の対象ではない） |
| ポーカー | スリーカード以上の役を作った 10 回勝負に勝ち越した（#2551。1 回ごとの決着は記録・評価の対象ではない） |
| 将棋・チェス・囲碁・オセロ・五目並べ | 「ふつう」以上の CPU に勝った（`CPUStrength.isReviewWorthy`。人間同士は含まない） |
| 麻雀（4 人打ち）・大富豪 | 1 位で終えた（＝勝ち。既定のまま） |
| 2048 | 2048 のタイルを作った（＝勝ち。既定のまま） |

### 答えた人と新しいゲームの感想カード（#3061）

- **答えた人**: 感想カードで「App Store で感想を書く」を押した人。`PlayLog` の `review_answered_v1`（真偽値 1 個）に記録し、
  以後は上の条件 1〜6 をすべて満たしても出さない（iOS は実際に評価したかを教えないため、これが唯一の目印）。
- **新しいゲームの感想カード**: `NewGames.currentVersionIDs` のゲームを 1 局最後まで遊んだ直後（勝敗を問わない）に、
  条件 1〜6 を飛び越えて **1 人につき 1 回だけ**（版ごとにリセットしない。`review_newGameCardAsked_v1`）。結果画面の 1.0 秒後に、
  画面上のオーバーレイ（`ReviewRequestPrompt.swift`）で「新しいゲームはどうでしたか？」＋「App Store で感想を書く」／「あとで」を出す。
  「感想を書く」は App Store のレビュー記入画面（`ReviewRequestService.writeReviewURL`）を開く。行き先は 1 つで、感想の中身による振り分けはしない。
  同じ決着で通常の評価リクエストと重なったらカードを優先する。
- 保存は真偽値 2 個（`review_answered_v1`・`review_newGameCardAsked_v1`）。端末内のみ・サーバ送信なし・増えない。「プレイ記録を消去」で消える。
- 解析は `review_prompt`（`kind` = regular\|new_game_card、`step` = shown\|write_review\|later\|os_requested、`trigger` は下記の節目のときだけ。下記「解析仕様」）。

### 遊んだ日数の節目（#3078）

アプリを開いた日の合計が **7 日・30 日**に達した日に、勝敗を問わず OS の評価ダイアログを 1 回依頼する（勝ちの少ない人にも届ける）。

- **数え方**: `PlayLog.recordAppOpenDay`。起動・前面復帰・ハブに戻った・決着のたびに呼び、同じ日は何度でも 1。
  端末の時計を戻されても増えない（最後に数えた日以前は数えない）。決着した日だけを数える `playDays`（連続プレイ日数・きろくの「遊んだ日数」）とは別物。
- **出す場所**: ハブに戻った（`HubView` の `path` が空になった）ときと、リザルト（`gameDidFinish`・敗北・引き分けも含む）。
  **起動直後・プレイ中には出さない**（起動は `appDidOpen()` で数えるだけ）。予定を立てたら 1.0 秒待ち、その前に画面を離れたら破棄する
  （ハブは NavigationStack の根でゲームの下に残るため、`hubReviewRequestPrompt(isActive:)` でハブが前面にある間だけ実行する）。破棄した節目は消費しない。
- **共通仕様**: 答えた人には出さない（C）、前回のお願いから 15 日以内なら出さない（A）。条件 2〜5（勝利数・同一バージョン 1 回）は課さない。
- **競合**: 感想カードの予定があるときはカードを優先し、節目は次の区切りに回す。勝ちの見せ場の予定と重なったら見せ場を優先する。
- **1 回まで**: 節目ごとに 1 回（`review_daysMilestoneAsked_v1` に出し終えた最大の節目を記録）。間隔で出せなかった節目は、明けた最初の区切りで出す。
  7・30 日がまとめて未消化なら大きい方 1 回で両方を済ませる。
- **保存**: 整数 3 個（`review_openDays_v1`・`review_lastOpenDay_v1`・`review_daysMilestoneAsked_v1`）。端末内のみ・サーバ送信なし・増えない。「プレイ記録を消去」で消える。
- **解析**: `review_prompt` の `trigger` = `days_7` \| `days_30`（見せ場の勝ちには付けない）。

禁止: 独自の「楽しんでいますか？」画面で振り分けてから OS の評価に回すこと（ガイドライン違反のおそれ）、
評価と引き換えの特典。

## 中断したゲームのお知らせ（#663・v1.1.5）

中断データを持ってハブへ戻った人にだけ、1 日ほど後に「「将棋」が途中のままです」をローカル通知で 1 件届ける。
汎用の「遊びに来てね」・デイリー通知・リモートプッシュは送らない。
本文は、ハブのタイルと同じ進み具合（`GameRegistry.resumeProgress`。将棋・チェスは「N 手目」、ナンプレは「残り N マス」等）が
あるときだけ「中断時は〇〇。続きから、そのまま遊べます。」とする（予約時点の中断データから作る・#3075）。無ければ固定文のまま。

- **規則は Core の `ResumeReminderService` / `ResumeReminderPolicy`**、OS へ渡す部分は App の
  `UserNotificationReminderScheduler`（`UNUserNotificationCenter`）。予約済みの一覧は OS が持ち、アプリ側に保存先を増やさない
- **予約**: `GameServices.gameDidLeave` で中断データがあるとき。ゲーム画面を出したままバックグラウンドへ入った中断（ホームボタン・アプリ切替）も、
  ハブが `scenePhase` を見て `gameDidEnterBackground` で同じ判定により予約する（#1951。離脱計測・画面の世代には触らない。許諾が未決定でも要求しない）。知らせるのは 24 時間後で、それが 21 時〜9 時に
  当たるなら次の 9 時へずらす（最大 36 時間後）。同じゲームは 1 件に置き換え、全体で 3 件まで（あふれたら古い中断から外す）
- **取り消し**: そのゲームを開いた（`gameDidOpen`）・バックグラウンドから同じ画面へ前面復帰した（`gameDidReturnToForeground`）・中断データが消えた（`ClearObservingSnapshotStore` が `clear` を捕まえる）・そのゲームを設定で非表示にした（`gameDidHide`・#810）・設定でオフにした
- **許諾**: 起動時には求めない。初めて予約するときに標準の許可ダイアログで明示的に求める（会長決裁 2026-09-21・#1219。
  以前は `.provisional` で静かに求めていたが、この決裁で更新された）。拒否されていれば何もしない
- **対象外**: `GameModule.resumesFromSnapshot == false` のゲーム（中断データから局を復元しないチャリンコおじさん）と、設定で非表示にしたゲーム（#810。予約もタップからの遷移もしない）
- **タップ**: `AppDelegate` が受け、ハブが `game_open{source: "resume_reminder"}`（#1950 で `notification` から分離） の導線でそのゲームを開く
- **止める経路**: 撮影モード・DEBUG ビルドでは予約しない。設定の「お知らせ」トグル（#1508 で久しぶり通知と統合）。動作確認は `-simulateNotificationTap <gameID>`（DEBUG のみ）

## ゲーム別の仕様（v1.1.5 以降で入ったもの）

### スパイダーソリティア（#717）

- 札は常に 2 組 104 枚。難度はスートの数（`SpiderSuitCount`）で、1 スート（入門・♠×8 組）/ 2 スート（標準・♠♥×4 組）/
  4 スート（上級・4 種×2 組）。局の開始時に `SpiderRuleSet` として焼き込み、中断データにも書く（1局=1RuleSet）。
  初回は開始シートを出さず 1 スートで配る
- 配札は解けることを確かめた種（`SpiderVerifiedSeeds`）から選ぶ。種の数は 1・2 スートが各 400、4 スートが 59（2026-09-15 時点・#914）
- **「新しいゲーム」は直前に配った種を除いて選ぶ**（`SpiderDealer.randomVerifiedSeed(for:excluding:)`・#914。
  4 スートは種が 59 個しかなく、除かないと 1 回あたり 1/59 で同じ配札が続けて出る）。スート数を変えたときも
  一律に除く。**フリーセルも同じ仕組み**（`FreeCellDealer.randomVerifiedSeed`）で直前の配札を除いて選ぶ
- **記録**: `GameScore.variant` を **3 難度すべてに付ける**（`1suit` / `2suit` / `4suit`。ナンプレと同じ）。新規のゲームで

### 大富豪: 決着した階級の持ち越し（#1066 #1103・`release/v1.1.6`）

決着した順位は、**盤面を持たない軽い記録 `DaifugoCarryOver`（順位 + 献上免除フラグの 2 つだけ）**にして次のゲームへ持ち越す。
リザルトからハブへ戻って開き直しても、次のゲームでカード交換（献上）が起きる。

- **保存先は `SnapshotStore` だが、キーは `gameID` ではなく `"daifugo-carryover"`**（`DaifugoModel.carryOverID`）。
  **`SnapshotStore` のキーは必ず `gameID`、という読み方をしない**——中断データと別枠の軽い記録を置く用途にも使う。
  ハブの「続きから」は `gameID` のキーしか見ない（`GameModule.hasResumableSnapshot`）ので、この記録が残っていても
  「途中の対局」としては数えられない
- **書く**: 決着時（`concludeGame`）と、広告で免除を立てた直後（`waiveExchangeAfterAd`）の 2 か所だけ。
  **配った時点（`startGame`）では書かない**（#1146）。決着のたびに上書きするので、1 度の階級が何ゲームも効き続けることはない
- **消す**: 通常の経路は **その局の 1 手目が中断データとして保存された時点**の 1 か所だけ（`persist()`・#1103。
  ほかに、順位が人数ぶん揃っていない異常系で持ち越し自体を捨てる分岐が `persistCarryOver()` にある）。
  **配った時点では消さない**——配ったばかりの局は中断データを保存しない（`isUntouchedDeal`・#240）ため、配った時点で
  消すと「開いて・1 手も出さずに閉じて・開き直す」だけで交換ゼロの配りが手に入る。中断データの保存に失敗した回も
  あえて残す（消すと中断データも持ち越しも無い状態になり、同じ抜け道が書き込みエラーのときだけ再発する）
- **読む**: `init` で**中断データが無いときだけ**（対局中の中断データは順位を自分で持っているのでそちらが優先）
- 免除フラグ（#1048）を順位と同じ記録に入れるのは、順位だけ持ち越して免除が消えると**広告を見た人だけが損をする**ため。
  免除は直後の 1 ゲームで使い切る（大富豪⇔大貧民の 2 枚交換だけをスキップし、富豪⇔貧民の 1 枚交換は残る）
- **免除を使い切る場所は順位と揃える**（#1146）。`isExchangeWaived` を戻すのは **1 手目の保存（`persist()`）** と
  **決着（`concludeGame`。新しい階級を書き込む前）** の 2 か所で、**配った時点では戻さない**。
  配った時点で戻していた版は、順位だけが 1 手目まで残るのに免除は焼き切れるという非対称を作り、
  「免除つきで配る → 1 手も出さずに離れる → 開き直す」で**広告を見た人だけが献上を取られた**（損得の向きが #1103 の逆）。
  決着側も要るのは、**1 手も出さずに投了した局は `persist()` を通らない**ため。そこを塞がないと免除が次の階級と一緒に
  持ち越され、1 本の広告で何ゲームでも献上を逃げられる。裏返しとして、**着手していない配りは何度配り直しても免除が効く**
  （順位側の #1103 と同じ性質。本番は種を渡さず毎回シャッフルするので手札そのものは配り直すたびに変わり、
  実質「免除を保ったままの引き直し」になる。着手＝その配りの確定、という線の引き方を順位と免除で揃えた結果であり、
  広告 1 本の対価の範囲に収まるとして許容している）

### 大富豪: ローカルルール「しばり」（#2605・`release/v1.1.14`）

採用ルールは革命 / 8切り / 反則上がり（#89）に、**任意で選べる「しばり」**を足した（同じスートが 2 回続いたら、場が流れるまでそのスートしか出せない）。既定はオフで、オフのときの挙動は従来と完全に同じ。

- **1 局 = 1 RuleSet**: `DaifugoRuleSet`（`isBindEnabled`）を局の開始時に `preferredRuleSet` から `ruleSet` へ焼き込み、中断データ（`DaifugoSnapshot.ruleSet` / `bindSuits`。どちらも optional で、旧データは標準ルールで復元）にも書く。対局中に選び直しても今の局は変わらない
- **掛かる条件**: 場に組があり、直前の組と出した組の**ジョーカー以外のスートの集合が同じ**（空でない）とき（`DaifugoRules.nextBindSuits`）。ペアは集合一致。親の最初の 1 手では掛からない。ジョーカーだけの組はしばりを作りも解きもしない
- **しばり中の制約**: ジョーカー以外の札がすべてしばりのスートでなければ出せない（`satisfiesBind`）。出せる判定・ヒント・出せない理由・CPU の候補（`legalPlays` / `greedyPlay`）に同じ `bindSuits` を通す。革命中も同じに働く
- **解ける**: 場が流れたとき（8切り・全員パス）と決着で空に戻す（`clearField` / `concludeGame`）
- **選択の保存**: `SnapshotStore` のキー `"daifugo-rules"`（`DaifugoModel.ruleSetID`。中断データ・持ち越しとは別枠で、ハブの「続きから」には影響しない）。次のゲーム・次回起動にも引き継ぐ
- **導線**: 開幕には出さない（#192 で開幕モーダルを廃止済み）。右上の「新規」の開始シート（`DaifugoNewGameSheet`・`GameSetupSheet` の `.versus`）に、#2604 の「CPU の強さ」と並べて「しばり なし／あり」を置く（独自のシート・「⋯」メニュー・リザルトのボタンは持たない）。表示は場のヘッダーの「しばり ♠」の札（VoiceOver は「しばり中、スペードのカードだけ出せます」）

### 大富豪: ローカルルールの拡張と一言説明（#2721・`release/v1.1.15`）

「しばり」だけだった `DaifugoRuleSet` を 5 項目に広げた: `isEightCutEnabled`（8切り・既定オン）/ `isBindEnabled`（しばり・オフ）/ `isSequenceEnabled`（階段・オフ）/ `isDownfallEnabled`（都落ち・オフ）/ `isFoulFinishEnabled`（反則上がり・オン）。既定は従来の採用ルールと同じで、**1 局 = 1 RuleSet**・保存先（`daifugo-rules`・中断データ）も上の「しばり」の節のまま。欠けたキーは既定で補って読むので旧データ（しばりだけ）も読める。選ぶ場所は開始シートのトグル 5 行。

- **階段**: 同じスートの連番 3 枚以上（強さの並び 3…K・A・2 で連番。2→3 の輪はつながない）。場と同じ枚数で、場が階段のときは階段だけ・場が同じ数字の組のときは組だけが出せる（`DaifugoPlayShape`）。ジョーカーは穴か端を埋め、強さは出す側に有利な置き方で数える。階段は革命にならず、8 を含む階段は 8切りが働く。CPU は階段も合法手に数え、親番では弱い札から始まる階段を優先する（`orderingStrength`）
- **8切りなし**: 場は流れない。8 は反則上がりの札にも数えない（`isFoulFinish(_:ruleSet:)`）。反則上がりなしの局では最後の 1 手が 2・ジョーカーでも順位を落とさない
- **都落ち**: 前のゲームの大富豪（`lastRanking.first`）が 1 位で上がれなかったら、投了者を除く最下位に落とす（`DaifugoRules.downfallPlayer` / `ranking(previousTycoon:)`。反則で下がった場合も含む）。1 ゲーム目は起きない。`downfallPlayer` は決着した局だけ持ち、次のゲームで消える（中断データには載せない）。前の順位 `lastRanking` は中断データ・持ち越し（`DaifugoCarryOver`）から復元する
- **起きた瞬間の一言説明**: 8切り・革命・革命返し・しばり（掛かった瞬間）・反則上がりが起きると `ruleNotice`（`serial` 付き）を入れ、`DaifugoView.ruleNoticeBanner` が場の上に 3.5 秒出す（`.task(id: serial)`）。VoiceOver にも読み上げる。保存せず、決着・次のゲームで消える
- 記録は 1 本のまま（ルール別には分けない。CPU 強さ別の区分が既にあり、二重に割ると薄まるため。必要なら別 Issue）

  負け・引き分けは 0 点。CPU も勝った回に CPU の役の点が入り、**10 回の合計点が多い側が勝負の勝ち**（同点は引き分け）
- 画面の上の帯は「n回目 / 10」「合計 n点」「CPU n点」。卓の中央は勝負の前が「いまの役・勝てば +n点」、決着後がその回の点。
  10 回目のあとはまとめ（合計点・勝った回数・作った一番強い役・自己ベスト・「もう一度 10回勝負」）を出す
- チップ・アンティ・ポット・チェック/ベット/コール/フォールド・役ボーナスのルール・ダブルアップ・チップ切れ復活は**全部削除**
- **リワード広告: もう 1 回交換**（`purpose` は `undo`）。交換したあと勝負する前に出し、**1 回の勝負につき 1 回**。
  見終えたら交換の段に戻り、2 回目の交換のあとはそのまま勝負になる
- **記録**: 区分キー `round10`（`poker#round10`・区分名「10回勝負」）の合計点。以前の記録（`poker`・`poker#bonus`）は
  持ち点の意味が違うので `PlayLog.retiredRecordKeys` で読み込み時に捨てる
- **Game Center の順位表（`asobiba.poker.chips`）へは送らない**（`GameScore.isLeaderboardEligible = false`）
- **解析**: 1 回目を配った時点で `game_start`、10 回目の決着で `game_end` を 1 回（`result` は合計点の比較）。
  評価リクエスト・おすすめも 10 回目の決着のときだけ
- **中断データ**: 交換中・勝負の前・各回の結果を保存する（`PokerSnapshot.format = 2`）。#2551 より前の形式は decode できず、
  読み飛ばして開始シートから始める（ファイルは消す）
- 静止画: `docs/design/poker-points-2551/`（iPhone 17 幅と SE 幅。SE の決着の画は縦に収まらずスクロールになるので中身の高さで描いた）

### ブラックジャック・ポーカーの単発戦（#2860・`release/v1.1.14`）

10 回勝負とは別に、**1 回だけで終わる「単発戦」**を選べる。ポーカーは開始シートの「遊び方」、ブラックジャックは配る前の
「10回勝負で配る／単発戦で配る」で選ぶ。決着後は「遊び方を選ぶ」で選び直せ、「もう一度」は同じ形で始め直す。

- **型**: `PokerSessionFormat` / `BlackjackMatchFormat`（`tenRounds` / `single`）。回数は `rounds`（10 / 1）。単発戦は最初から最後の回なので
  「最終回」のバッジ・帯の強調は出さない（`showsFinalRoundMark`）
- **記録**: 区分キー `single`（`poker#single` / `blackjack#single`・区分名「単発戦」）。10 回勝負の記録（`round10` / `match10`）とは別。
  点はその 1 回で入った勝ち点。Game Center へは送らない。ブラックジャックの `match10` にも表示名「10回勝負」を付けた
- **解析**: 単発戦は 1 回で `game_start` / `game_end` が各 1 回、`mode = single_round`（`AnalyticsMode.singleRound`。ポーカー・ブラックジャック共通で、
  ゲームは `game_id` で分かれる）。10 回勝負は従来どおり `mode` を送らない
- **勝敗**: ポーカーは合計点（1 回なのでその回の勝敗）、ブラックジャックは回のまとめ結果（スプリットで一勝一敗でも点が入れば勝ち）
- **広告**: 負けた回のやり直し（BJ）・もう 1 回の交換（ポーカー）は単発戦でも 1 回まで使える
- **中断データ**: `format` / `sessionFormat` を optional で追加。無い旧データは 10 回勝負として復元する

### ブラックジャック・ポーカー: 復活で戻る**自分の**チップは無料のやり直しより必ず多い（#499 #523・`release/v1.1.6`）

※ブラックジャックは #2552、ポーカーは #2551（どちらも `release/v1.1.13`）でチップをなくしたので、この節は v1.1.12 までの経緯
（それぞれ上の「10 回勝負」節）。

チップ切れからリワード広告で復活したときに**自分に**戻るチップ（`reviveChips`）は、**無料でやり直したとき
（`initialChips`）より必ず多くする**（#523 の会長決裁 C 案）。復活は順位表に載らないため、少ない枚数だと
無料のやり直しの完全な下位互換になり、実際に `revival` が 0 件だった。
**多くするのは自分の側だけで、ポーカーの CPU は復活でも `initialChips`（100）のまま**——増やすと復活の旨味が消える。

| | 広告で復活（`reviveChips`） | 無料でやり直す（`initialChips`） | 倍率の理由 |
|---|---|---|---|
| ポーカー（自分） | **150** | 100 | CPU との 1 対 1 ではチップの多さがそのまま勝ちやすさになるので 1.5 倍に留める |
| ポーカー（CPU） | 100（`initialChips` のまま） | 100 | 復活しても CPU 側は増やさない |

- 導線の文言はどちらもこの定数から作る（枚数の数え違いを 1 か所に閉じる）。復活は **1 セッション 3 回**まで（#2012・#2022・`release/v1.1.11`。`maxRevivesPerSession = 3`・使った回数 `reviveCount`。
  2 回目・3 回目も同じ枚数で戻り、1 回でも使ったセッションは順位表の対象外。ボタンは「あとN回」（残り 1 回は「最後の1回」）、使い切り後は「復活はこのセッションで3回使いました」。
  中断データには `reviveCount` を Optional で足し、旧鍵 `hasRevivedThisSession` も残す——旧データ（旗のみ）は 1 回使用済みとして読む。
  ※ルーレットは #2545 で削除済み）
- **復活を使ったセッションは Game Center の順位表へ送らない**（BJ は `GameScore.isLeaderboardEligible = !hasRevivedThisSession`、
  ポーカーは既定と違うルールでも外れるので `rules.isLeaderboardEligible && !hasRevivedThisSession`）。
  送ると「広告を何回見たか」の表になるため。**ローカルの自己ベストには残す**ので、分けるのは `GameScore.variant` ではなく
  `isLeaderboardEligible` のほう（`variant` を足すと保存先が変わって過去の自己ベストが参照されなくなる）
- リワード救済の `purpose` は `revival`
- **復活したセッションは局が無くても中断データを持つ**（残高と復活済みの印だけ）。BJ は `hands`/`playerHand` を空のまま
  `chips` を `reviveChips`・`hasRevivedThisSession = true` で保存し、ポーカーは `phase` を `.idle` に戻して保存する。
  どちらも `GameModule.hasResumableSnapshot` が偽になるため、ハブの「続きから」バッジ・`game_open` の `resume` には
  出ない（局を持たない中断データは「続き」ではない、将棋・チェスの見返しと同じ考え方・#809）
- **開き直したときの戻り先はゲームごとに違う**: ブラックジャックは賭け待ちに戻り、**ポーカーは開始シートに戻る**
  （`phase == .idle` は「まだ局が始まっていない」と同じ状態のため）

### 重ねた札の段差と見出し（フリーセル・スパイダー共通・#1095・`release/v1.1.6`）

札の幅は「画面幅 ÷ 列の数」でほぼ決まり横には広げられない一方、**縦は盤の下に大きく余る**。
そこで段差（重なりの間隔）を固定比にせず、**いちばん長い列が盤の下端に収まる範囲で広げる**計算を
`Core/CardTable.swift` の `CardStackLayout` に置き、フリーセルとスパイダーで共有する（同じ役割の UI は同じ見た目にする）。
**クロンダイク（ソリティア）はこの計算を使っておらず、従来の固定比のまま。**

- 入力は札の幅・高さ、場札に使える縦の高さ、列ごとの伏せ札／表向きの枚数。出力は表向きの段差・伏せ札の段差・
  列が押せる範囲の高さ・帯だけ見えている札の見出しの寸法（`CardStackIndexMetrics`）
- 段差は**全列で同じ値**（列ごとに違うと見た目が揃わない）。下限は従来の固定比（表向き 0.24・伏せ札 0.13）で
  **今より詰めることはしない**、上限は表向き 0.45（広げすぎると 1 本の列に見えなくなる）。伏せ札は表向きと同じ倍率で伸ばす
- 盤の左右の余白は 4pt（帯やボタンの `Theme.pad` 16pt より詰める）、最長列の最後の札と盤の下端のあいだは 4pt 残す
- **帯に描く数字とマークの大きさは札の幅に比例させず、帯の高さ（＝段差）から決める**。「10♥」が札の幅に収まる上限を守る
- 列の下の空きを押しても、その列のいちばん下の札（空の列なら列そのもの）を押したことにする（`reachHeight` は盤の下端まで）

バカラ・七並べ（#1197/#1198）は `release/v1.1.6` に実装されたが、#1236 でハブ収録を見送り、
コードも削除済み（2026-09-21）。

よく遊んでいたのに最近開いていないゲームへ、最終プレイから7日・30日・60日後の3回「「将棋」、久しぶりに遊んでみませんか？」を

- **規則は Core の `ReengagementReminderService` / `ReengagementReminderPolicy`**、OS へ渡す部分は App の
  `UserNotificationReengagementScheduler`（`UNUserNotificationCenter`）
- **複数ゲームのスレッドが並行しうる**（上限なし・会長決裁 2026-09-21・#1229）。新しい対象が選ばれても、既存の
  アクティブなスレッドはキャンセルしない。同じゲームが再度選ばれたとき、アクティブなスレッドの起点（最終プレイ日時）が変わっていなければ何もせず、
  変わっていれば（遊んだ後など）7・30・60日後を起点から組み直す（#2939）
- **状態は端末内の `UserDefaults` に永続化する**（`ReengagementReminderStore`。サーバ送信なし）。OS の予約一覧だけでは
  「60日後通知が発火した」という過去の事実を確定できないため、スレッドの起点（そのスレッドを作った時点の最終プレイ日時）を
  ここに永続化する:
  - `reengagement_activeThreads_v1` — アクティブなスレッド（ゲームID → 起点になった最終プレイ日時）
  - `reengagement_lastThreadAddedAt_v1` — 最後に新しいスレッドを追加した日時（ゲームごとではなく全体で1つ）
  - `reengagement_permanentlyStopped_v1` — ユーザー全体の永続停止フラグ
- **対象判定**: アプリがバックグラウンドに入るたびに判定し直す。**判定時点での未プレイ日数は問わず**（#2939。遊んだその日に
  離脱した人にも予約するため。以前の「7日以上未プレイ」条件 `minimumIdleDays` は廃止）、プレイ回数が1回以上で最終プレイ日時のある
  ゲームのうち**通算プレイ回数が最も多いもの1件**を候補にする。同率はハブの並び順（先頭）で決める
- **新規スレッドのクールダウン**: 「他のゲームのスレッドがアクティブなまま別のゲームのスレッドを足す」ときだけ、直近のスレッド追加から
  `newThreadCooldownDays`（3）日以上経つまで見送る（通知が増えすぎるのを防ぐ・会長決裁 2026-09-21。#2939 で対象を限定）。
  同じゲームの組み直しと、他にアクティブなスレッドが無いときの追加には掛けない。`reengagement_lastThreadAddedAt_v1` は
  新しいスレッドを足したときだけ更新する
- **発火**: 各スレッドの起点になった最終プレイ日時の7日後・30日後・60日後の`deliveryHour`時（19時。過去に落ちるものは予約しない）
- **同日衝突の解決**: 複数スレッドの発火予定が同じ暦日に重なったら、日数が大きい方（より切迫している方）だけ残す。
  小さい方はその回だけスキップする（スレッド自体は他の予定日が残っていれば続く）
- **永続停止**: 60日後通知の発火予定時刻から24時間経っても未反応（`lastPlayedAt` が不変）なら、そのユーザー全体で
  この機能を永続的に停止する（会長決裁 2026-09-21）
- **取り消し**: そのゲームを開くと、**そのゲームのスレッドだけ**止める（`gameDidOpen`。他のゲームのスレッドは続く）。
  設定の「お知らせ」トグルをオフにする・「プレイ記録を消去」する（#1269）と、全スレッド・状態を消す
- **許諾**: 判定は背面へ入る処理から呼ばれるため、**許諾が未決定のときは許可ダイアログを求めず、予約もしない**（#2938。続きのお知らせ #1951 と
  同じ。許可済みのときだけ予約する）。許可ダイアログは前面の導線（続きのお知らせ・挑戦回数のお知らせ）で出る。**`.provisional` は使わない**
  （会長決裁 2026-09-21。#663 も #1219 で同じ方式に揃え済み）。そのため `notification_permission` の `trigger=reengagement` は現在発火しない
- **対象外**: 設定で非表示にしたゲーム
- **タップ**: `AppDelegate` が受け、ハブが `game_open{source: "reengagement"}`（#1950 で `notification` から分離） の導線でそのゲームを開く
- **止める経路**: 撮影モード・DEBUG ビルドでは予約しない。設定の「お知らせ」トグル

### ボタンの回数表示と広告の補充（共通ルール・#1897・会長決裁 2026-10-07）

広告は**あくまで追加の補充**であって、回数そのものには含めない。回数制のボタン（ヒント・戻す・待ったなど）が持つ「数字」と「広告」の関係は、ゲーム・ボタンを問わず次の4点に統一する:

1. ボタンの数字は**いま使える回数**（無料枠＋すでに広告で補充済みの分）。広告でこれから足せる分は数に含めない。
2. 数字は常に出す。**0 になったら**、数字（0）とあわせて「広告を見て追加できる」ことが分かる表示にする
   （広告は補充の手段であって回数ではない）。
3. 広告を見たら、その分が数字に足される（例: ヒント +1、戻す +3）。
4. 広告での補充に上限がある操作は、上限まで使い切ったら 0 のまま、追加の案内も出さない。

**0 のときの見た目（会長決裁 2026-10-07「案3＋a′」）**: 0 で広告を見ると足せる状態**だけ**、ボタンの面と 2 行目を変える。
面は役割色 22% の淡い塗り＋役割色の枠 2pt（`GameActionCapsuleStyle`。数値は仮値）、2 行目は「0回 ▶ 広告を見て +N」
（N＝広告 1 本で足される数。ヒント・待った +1、戻す +3）。通常（n ≥ 1）は今までの塗りと「あと n 回」。広告での補充を
使い切った 0 は disabled（グレー＋0.55）の「あと0回」で広告の案内なし。実装は共通部品 `GameActionBadge`
（`.count(n)` / `.ad(gain:)`）で、盤ゲームのヒントは `GameActionBadge.hint(totalRemaining:needsAd:)` が
`BoardHintBudget` から「無料の残り」だけを数える（広告の 5 回を開始時の数字に合算しない）。保存形式は変えない。
**新しいゲーム・ボタンを足すときもこのルールに従う**。

### リワード救済（`RewardedRescue`・#526）

各ゲームの View に同じ形で散っていた「連打ガード → 広告視聴 → 局ガード照合 → 適用 → 失敗アラート」の
5点セットを `Core/RewardedRescue.swift` の1か所に集約したもの（この設計により、新しい救済を足しても
連打ガードや局ガードの実装漏れが起きない）。ほぼ全ゲーム（2048・将棋・五目並べ・麻雀・麻雀ソリティア・
ソリティア・フリーセル・スパイダーソリティア・ポーカー・ブラックジャック・マインスイーパー・ナンプレ・オセロ・囲碁・
チェス・神経衰弱・ブロック崩し・チャリンコおじさん、`release/v1.1.5` の 2026-09-15 時点）が採用している。
2026-10-18 以降は、おじさんの荷物運びパズルも負けた結果から `continue` で 1 局 1 回だけ続けられる（#2013。入院＝腰痛ゲージを 50 に戻す・積み上がり＝荷物のある一番上から 4 段を片づける。得点は引き継ぎ、続けた局は順位表へ送らず、直前の負けは記録から取り消す。数値は仮置き）。
`release/v1.1.6` で大富豪が加わった（大貧民で決着したリザルトから、次のゲームの献上を免除する。`purpose` は `revival`・#1048）。
同じく花札こいこいが加わった（最終局で負けている局の結果画面から、1試合に1回だけ1局延長する。`purpose` は `continue`・#1049）。
`release/v1.1.7` の柵越えおじさん（v1.1.9 でハブに公開済み）は、1 日の挑戦回数を使い切った後、広告を見ると救済プレイを 1 回行える（保存済みの挑戦回数は増やさない）

`HomerunRecoveryButton` の 1 か所）。

## 解析仕様（Analytics・#158 / #500 / #659 / #780 / #1043 / #1348）

`CoreEngine/Analytics.swift` に**送信するイベントを下の表の9種だけに閉じた** `AnalyticsEvent` enum がある
（`reward_request` / `game_open` の2種は #659 で `release/v1.1.5` に、`share_tap` は #1043 で `release/v1.1.6` に、`reward_offer` は #780 で `release/v1.1.7` に。`notification_permission` は #2008 で `release/v1.1.11` に、`clear_exit` は #2848 で `release/v1.1.14` に。`survey_answer` は #1348 で足したが、アンケートの削除（#1956）で廃止。
main のコード（v1.1.9・v1.1.10 の公開版）には `surveyAnswer` のケース・`recordSurveyAnswer` / `gameDidAnswerSurvey`・`HomerunModel.submitSurvey` が互換のため残っているが、
入口が `HomerunSurvey.isOffered = false` で画面に出ないので実際には送信されない。#1956 を含む `release/v1.1.11` 以降ではケースごと削除済み。
v1.1.4 までの公開版は3種）。
呼び出し側（各ゲーム）は任意のキー・値を足せず、イベントを増やすには enum にケースを足す必要がある
（＝意図しないイベント発生や、ドキュメントと実装が知らないうちに乖離することを型で防ぐ設計）。

| `clear_exit` | 面をクリアした直後の画面を、次の面にも「もう一度」にも進まず離れた（チャリンコおじさんのステージ制。`GameAnalytics.leaveGame` の1か所・#2848） | `game_id` / `level`(`stage-N`) |

| `share_tap` | 自己ベストを更新したリザルトの**共有ボタンを押した**（`RecordLabel` の共有ボタン。共有シートで実際に送ったかは問わない） | `game_id` のみ |

- `game_id` の全量は**コード上の一覧を文書側で持たない**（`App/AppGameServices.swift` の
  `registry.modules.map(\.id)` から実行時に作られる）。新ゲームを `registry` に登録するだけで
  自動的に対象へ入るため、**このドキュメントに `game_id` の値そのものを列挙しない**
  （列挙すると新ゲーム追加のたびに手動同期が要り、漏れの温床になる。実際の値は各ゲームの
  `GameModule.id` を参照すること）
- `mode`（`AnalyticsMode`）は遊び方の区分（v1.1.5）。四人打ち麻雀は `tonpuu`（東風戦）/ `single_hand`（一局戦）/ `hanchan`（半荘戦・v1.1.15・#3098）、
  チャリンコおじさんは `stage`（ステージ制。面番号は `level` の `stage-N`）/ `endless`（エンドレス。`level` を送らない）。
  おじさんの荷物運びパズルは `backpain`（荷運びモード。旧称「腰痛モード」）/ `puzzle`（パズルモード）（#1920）。
  将棋は手合い（#2179・v1.1.12）で `even`（平手）/ `rook_player`・`rook_cpu`（飛車落ち。落とす側が自分／CPU）/ `bishop_player`・`bishop_cpu`（角落ち）。
  写像は各ゲームの `analyticsMode`（`MahjongGameLength` / `RunnerMode` / `ShogiMatchSetting`）に置く。一局戦は 1 対局が 1 局なので
  `game_start` が機械的に増える。回数を比べるときは `mode` で分け、時間で比べるときは `duration_sec` を使う。
  `game_end` の `mode` は開始時に焼き込んだ値で、途中で遊び方を替えて始め直したときも捨てたプレイの側の値が載る（#783・#785・#820）
- `cause`（`AnalyticsEndCause`・#796・`release/v1.1.5` から）は**そのプレイで最後にミスした原因**。
  ミスのたびにイベントは出さず（イベントの種類は増やさない）、各ゲームが `gameDidMiss` で原因を
  伝えると `GameAnalytics` が覚えておき、そのプレイの `game_end` に載せる。ミスの無いプレイ・ミスの
  概念が無いゲームは鍵ごと送らない。語彙は `pit`（穴）/ `rock`（岩・台座の正面）/ `bird`（鳥）/
  `animal`（犬・イノシシ）/ `sink`（沈む床で溺れた・#1089）の5値に閉じ、障害の種類を足しても
  enum を増やさない限り値は増えない（`sink` は「跳び越せなかった」穴とは直す先が違うので分けた）。
  いまはチャリンコおじさんだけが送る。ステージ制ではミスは決着ではなく `game_end` はクリア（win）か
  途中離脱（quit）でしか出ないので、「何にやられて諦めたか」＝離脱直前の死因として読む。
  GA4 のカスタムディメンション登録が要る（会長操作）
- `credit`（`AnalyticsCredit`・#1685・会長指示 2026-10-01）は**そのプレイが消費した回数枠**（`free` 無料 /
  `ad` 広告 / `bonus` 月を落としたご褒美）。柵越えおじさんだけが `game_start` と `game_end` の両方に載せ（枠ごとの回数・遊んだ時間を
  出すため）、イベントは増やさない。**枠の使う順は固定で 無料 → ご褒美 → 広告**（`HomerunLedger.nextCredit`・
  使った回数と今の付与だけから決まり、保存の形は変えない。もらった順ではないので、無料を使い切る前の遊びは「広告を見て遊んだ」に
  数えない）。DEBUG の `-homerunUnlimited`（回数を使わない）では載せない。回数制でないゲームは鍵ごと送らない。
  GA4 で枠別に見るには**カスタムディメンション `credit`（イベントスコープ）の登録が要る**（会長操作）。
- `level`（#1888・会長指示 2026-10-06）は**開始時に付けた値を `game_end` にも同じ鍵・同じ値で載せる**（面・難易度ごとの勝ち / 負け /
  途中でやめた・`cause`・`duration_sec` を結び付けて読むため）。`level` を持つ全ゲームに効き、イベントは増やさない。
  `GameAnalytics.sendEnd` の 1 か所から出るので決着・離脱・休憩からの再開のどれでも載り、休憩の控え（`RestEntry.level`）にも入るため
  アプリ終了をまたいだ再開でも落ちない（旧版の控えは `level` 無しで読み、鍵ごと送らない）。
  GA4 の `level` は `game_start` で送っているパラメータと同名なので、イベントスコープのカスタムディメンション登録済みなら追加の登録は要らない
  （登録の有無は GA4 管理画面でしか確認できない。会長操作）。
- `miss_count` / `miss_at` / `exit` / `clear_exit`（#2848・会長指示 2026-10-25）は**ステージごとの「ミスして離脱」「クリアして離脱」を GA4 で分けて読む**ための計測。
  ミスは `gameDidMiss` が 1 回ごとに数えて覚え、そのプレイの `game_end` に `miss_count`（回数）と `miss_at`（最後のミスの進行率。面の長さに対する %
  を 5 刻みに切り捨てた 0〜100。エンドレスでは送らない。エンドレスは 1 回のミスで決着するので `miss_count` は常に 1 で、集計は `mode` で絞る）を載せる。`exit=after_miss` は **quit のとき、直前のミスを挽回していない（走り直していない・
  `gameDidProgress` が再び呼ばれていない）プレイ**だけに載る（走行中に離れた quit は `exit` 無し）。クリア（win）の `game_end` は決着時に送信済みなので、
  その後の離脱は新イベント `clear_exit`（`game_id` / `level`）で出す。`level` が `stage-N` のプレイが win で終わったあと、次の面へも「もう一度」へも進まずに
  `leaveGame` したときの 1 回だけ（アプリを終了してクリア画面から戻らなかった場合は出ない）。GA4 の流れは
  挑戦=`game_start` → ミス→再挑戦=win の `miss_count`>0 → ミス→離脱=quit の `exit=after_miss` → クリア→次へ=次の面の `game_start` → クリア→離脱=`clear_exit`。
  **`miss_count` / `miss_at` / `exit` はカスタムディメンション（イベントスコープ）の登録が要る（会長操作）。**
- `hints_used`（#1326）は**そのプレイで使ったヒントの回数**（将棋・チェス・五目並べ・オセロは1〜8、マインスイーパーは1〜4・#2024、15パズルは1〜8・#1975、神経衰弱は1〜4・#2026、ソリティア・スパイダー・フリーセルは1〜8・#2025）。この10本だけが送る。
  各 Model が `BoardHintBudget.consume()` の成功ごとに `gameDidUseHint` を呼び、`GameAnalytics` が進行中の
  プレイに覚えて `game_end` に載せる。**送信は `sendEnd` の1か所**なので、決着（`finishPlay`）でも
  途中離脱（`leaveGame` / `restartPlay`）でも同じ値が載る。使わなかったプレイ・ヒントを持たないゲームは鍵ごと送らない。
  1手も指さずに捨てた局は従来どおり `game_end` 自体が出ない。休憩（再開できる離脱）をまたいでも数えは残り、
  アプリを終了したあとに「続きから」で復元した局も、休憩に入る時点（ハブへ戻るとき）と、アプリが背面に回る時点（#2300。ハブへ戻らず OS に終了された場合）の控えから取り戻す（下記 #1374。`cause` だけは控えに入れない）。
  GA4 のカスタム指標「ヒント使用回数」（範囲=イベント）は 2026-09-24 に登録済み
- パラメータの値（`result` / `level` / `purpose` / `source` / `mode` / `cause`）は `CaseIterable` な enum で定義し、
  `AnalyticsTests` に全量のテストを置く。文字列の引数で値を足せる口を作らない（#820。`mode` だけ `String?` だったため、
  文書に無い値が 23 分後に流れ込んだ）
- `level`（`AnalyticsLevel`）はゲームごとの難易度呼称をゲーム横断で読める値
  （`novice`/`beginner`/`normal`/`hard`。CPU 対戦の4段階から送られる）か、面を進めるゲームは
  `stage-N` に正規化して送る。写像は各ゲームの `analyticsLevel` に置く。`novice` は CPU 対戦の
  4段階化（`CPUStrength`・#1174・v1.1.6。上記「CPU 対戦の強さ 4 段階」）で追加した値で、既存3段階
  （`beginner`/`normal`/`hard`）の値・GA4 の既存の数字は動かしていない。型としては `expert`
  （ガチ）のケースも残っているが、「ガチ」が一旦見送り（#1283）のため現状は送信されない
- 送信は `GameAnalytics`（`Core/Analytics.swift`）が一括管理し、二重発火の抑制・経過秒の計測・
  離脱と休憩の切り分けをここ1か所に閉じ込める。個々のゲームは
  「開始した」「1手指した」「やり直した」「終局した」「画面を離れた」を伝えるだけでよい
- 離脱計測（`leaveGame(isResumable:)`）と中断のお知らせの予約（#663）は、ハブの「続きから」・`game_open` の `resume` と
  **同じ判定**（モジュールの `hasResumableSnapshot`）を使う。`GameServices.gameDidLeave` が App 層の差し込み
  （`GameServices.isResumable`・`App/AppGameServices.swift`）経由で呼ぶ。`snapshots.exists` だけで決めない（#1847）。
  差し込みが nil のテスト・プレビューだけ `snapshots.exists` に落ちる（`release/v1.1.11` から）
- 設定でオン/オフした境界をまたいだプレイは `game_start`/`game_end` の対応を保証しないため、
  トグル時点で計測中の状態を丸ごと捨てる（`discardPlayState()`。#212）
- `reward_request` と `game_open` はプレイの数え方（`game_start`/`game_end` の対応）に影響しない。
  `reward_ad ÷ reward_request` が完了率、`game_open` の `resume = 1` が「続きから」の再開プレイ
  （`game_start` は再開では送られないため、再開を数える唯一の手段）
- `game_open` の導線は遷移の値そのもの（`HubRoute`）に持たせる。タップの横で別の状態に書き留めると
  タップと path の変化の順序が保証されないため。`resume` も**タップした時点**の「続きから」の判定（ハブのバッジと同じ `GameModule.hasResumableSnapshot`・#809）で決める。
  `notification` は通知を種類別に分ける前の旧値（#1950 以降は発火点なし。既存の GA4 レポートの値を壊さないため語彙には残す）。
  `resume_reminder` は #663 の中断したゲームのお知らせ、`reengagement` は #1193 の久しぶりに遊ぼう通知、`challenge_return` は #1576 の挑戦回数が戻ったお知らせのタップで開いたとき（いずれも #1950・`release/v1.1.11` から）
  `first_pick` はハブ最上部の「はじめの1本」（#721。記録ゼロの初回だけ出る1枚）から開いたとき（`release/v1.1.5` から）
  `quick_action` はホーム画面アイコン長押しの項目（#1642。「続きから」可能なゲーム→最近遊んだゲームの最大4件。
  `RecentGames` と同じ並び・非表示除外で、バックグラウンドへ入るたびに `QuickActionService` が組み直す。`release/v1.1.9` から）
  `deeplink` はディープリンク `asobiba://game/<game_id>` で開いたとき（#2141。App 内イベント #1995 の審査で必須。
  スキームは `project.yml` の `CFBundleURLTypes`、URL → 遷移先は `DeepLink`（CoreEngine）の純関数、受け口は `HubView` の `onOpenURL`。
  未知・設定で非表示のゲームと `asobiba://` 単体はハブのまま。コールドスタート・起動中とも効く。`release/v1.1.11` から）
- `source` / `position` / `resume` は GA4 のカスタムディメンション登録が要る（会長操作依頼 #694）
- `share_tap`（#1043・`release/v1.1.6` から）は、「自己ベスト更新！」バッジが出た回だけ記録の行の末尾に出る共有ボタンを
  押した回数。20 本の `RecordLabel` の呼び出しは変えず、ハブの `navigationDestination` がゲーム画面ごとに
  `RecordShareContext`（ゲーム名・App Store の URL・押したときの処理）を環境値で配る（配られないテスト・プレビューでは出ない）。
  共有の文言は記録を前面に出し（`RecordFormat.shareMessage`。「あそびばの「2048」で記録更新！」＋リザルトの 1 行）、
  URL にキャンペーンのパラメータは付けない。載せるのは `game_id` だけなので GA4 の新しい登録は要らない。
  `ShareLink` は完了を知らせないため「送った数」ではなく「押した数」として読む。チャリンコおじさんは `RecordLabel` を
  使わないので対象外
- `reward_offer`（`RewardOfferResult`・#780・`release/v1.1.7` から）の**提示**は、広告を見るかどうかを選ばせる画面
  （確認アラート・コンティニューの幕・リザルトの復活ボタン）が出たこと。無料で済む確認（無料の待った）は含めない。
  各画面は `rewardOffer(_:for:isPresented:services:gameID:)` 修飾子で「出ているか」だけを渡し、押したかどうかは
  `RewardedRescue` の要求が知っている。`result` は、広告ボタンを押して先読み済みの広告があれば `accepted`、
  無ければ `not_ready`（その場で読み込む。#658 の先読みで減る値）、押さずに閉じた・画面を離れたら `declined`。
  見なかった後に同じ画面でもう一度押しても提示は 1 回のまま（タップの数は `reward_request` が持つ）
  - **提示の瞬間が無い面は数えない**: ナンプレのヒント（常設のボタンで、確認を挟まずに広告へ進む）と、
    将棋・チェス・五目並べ・オセロのヒント（無料 3 回を使い切ったあと、「⋯」メニューの項目から確認を挟まずに広告へ進む・#1500）と、
    15パズルのヒント（同じく操作の段のカプセルから・#1975）・マインスイーパーと神経衰弱のヒント（#2024・#2026）・ソリティア、スパイダー、フリーセルのヒント（#2025）。
    この面は `reward_request ÷ game_start` で読む。対象の一覧は `AnalyticsTests` の `RewardOfferWiringTests` が固定する
    （`unpresentedRescues` に `GameSudoku` / `GameShogi` / `GameChess` / `GameGomoku` の `hintRescue` の 4 件）
  - 読み方（週次会議）: **受諾率** = (`accepted` + `not_ready`) ÷ `reward_offer`、**先読み不足率** = `not_ready` ÷
    (`accepted` + `not_ready`)、**提示率** = `reward_offer` ÷ 該当場面の発生（コンティニュー・復活は `game_end` の `loss`、
    待った・戻す・並べ替えは `game_start`）。いずれも `purpose` × `game_id` で分けて読む。`reward_ad ÷ reward_request` の完了率と合わせると、
    提示 → 受諾 → 視聴完了の漏斗になる
  - `result` は `game_end` と同じパラメータ名で、値の集合が別（イベント名で分けて読む）。GA4 の登録は #1002（会長操作）

## テーマ / デザイン

`Theme.swift` で一元管理:
- メインカラー: `Theme.coral` (オレンジ系)
- アクセント: `Theme.teal` (青緑) / `Theme.yellow` / `Theme.ink`
- カードスタイル: `.popCard()` modifier (白背景 + 影)
- 背景: `.popBackground()` modifier
- フォント: `.rounded` デザイン
- モーダル（シート）は縦長（`.large`）固定（#2096）。`.presentationDetents` は `[.large]` 以外を使わない。`ModalDetentScanTests` で強制

ゲームカードのアクセントカラーは `Theme.palette` からインデックス順に自動割り当て。

### 標準ダイアログのボタン色（#1874・`release/v1.1.11` から）

- 標準ダイアログ（`.alert` / `.confirmationDialog`）のボタンの文字色は `Theme.dialogTint`
  （ライト `#C93D2E`・白に対し 5.0:1、ダークは `coral` のまま）。アプリ全体の tint の `coral`（2.7:1）では
  OS のすりガラスの上で文字が沈むため、ダイアログだけ濃くした（2026-10-08 会長決裁・案 C。ダークのすりガラスは
  暗い面なので濃くすると逆に読めなくなる）
- **ダイアログは必ず `.dialogs { anchor in anchor.alert(...) }` の形で付ける**（View に直接付けない）。
  ボタン色は modifier を付けた位置の `tint` 環境で決まるので、View 本体に `.tint` を当てると画面側の部品まで
  変わってしまう。`.dialogs` は同じ大きさの空ビュー（`DialogAnchor`）を背景に敷いてそこへダイアログと tint を
  付けるため、ダイアログだけが変わる。直接付ける書き方は `DialogTintScanTests` が落とす
- `role: .destructive` のボタン（新規対局・投了など）はシステムの赤のまま（tint は及ばない）

## アクセシビリティ

### アニメーション（Reduce Motion 追従・#210）

**新規のアニメーションは必ず `Core` の `Motion` ヘルパー経由で書く**（素の `withAnimation` /
`.animation(_:value:)` を直接使わない）。

| 用途 | 使うもの |
|---|---|
| 宣言的な指定 | `.gameAnimation(_:value:)`（`.animation(_:value:)` の代わり） |
| 命令的な指定 | `withGameAnimation(_:_:)`（`withAnimation(_:_:)` の代わり） |

OS の「視差効果を減らす」が ON のときはアニメーションを `nil`（＝即時反映）に落とし、
**状態変更そのものは必ず実行する**。OFF のときは要求どおりのアニメーションを通すので、
既定の見た目は変わらない。

理由は2つ。①盤面の駒・カード・牌が動く演出は前庭障害・動揺病のあるユーザーに直接影響する。
②App Store の Accessibility Nutrition Labels に **Reduced Motion** の宣言項目があり、
基準は「アニメーションを減らした状態でもすべての一般的なタスクを完了できること」。
1箇所でも追従しないと申告が成立しない。

この規約は `AccessibilityTests` の「アニメーションは Core のヘルパー経由でのみ書かれている」で
機械的に担保している（`Sources/Core` 以外に素の呼び出しが混じるとテストが落ちる）。
